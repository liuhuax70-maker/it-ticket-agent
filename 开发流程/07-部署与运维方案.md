## 1. 目标与原则

| 目标 | 说明 |
| --- | --- |
| 一键部署 | `docker-compose up` 拉起全部服务，干净环境可复现 |
| 数据不出内网 | 生成与向量化全本地，无外部大模型 API 依赖 |
| 配置与密钥分离 | 全部通过环境变量注入，不写死在代码/镜像 |
| 可恢复 | 关键数据卷持久化，可备份与重建 |
| 易运维 | 健康检查 + 日志 + 明确 Runbook，个人也能维护 |
| 渐进演进 | MVP 单机 compose，后续可平滑过渡到多机/K8s |

## 2. 部署架构

### 2.1 服务拓扑（单机 Compose）

```
                    ┌──────────────────────────────┐
   客户端 ──:8000──►│  api (FastAPI, SSE)          │
                    │  · 依赖 milvus / ollama       │
                    └───────┬──────────────┬───────┘
                            │              │
              ┌─────────────▼───┐   ┌──────▼─────────┐
              │ milvus :19530   │   │ ollama :11434  │
              │ (向量 + BM25)    │   │ (Qwen2.5)      │
              └───┬─────────┬───┘   └────────────────┘
                  │         │
        ┌─────────▼──┐  ┌───▼────────┐
        │ etcd :2379 │  │ minio :9000│
        │ (元数据)    │  │ (对象存储) │
        └────────────┘  └────────────┘
```

### 2.2 服务职责

| 服务 | 职责 | 对外端口 | 内部依赖 |
| --- | --- | --- | --- |
| `api` | FastAPI 服务、SSE、编排 | 8000 | milvus、ollama |
| `milvus` | 向量 + BM25 检索 | 19530 | etcd、minio |
| `etcd` | Milvus 元数据 | 2379（仅内部） | — |
| `minio` | Milvus 对象存储 | 9000（仅内部） | — |
| `ollama` | 本地大模型推理 | 11434 | — |

> 生产建议：除 `api`（及必要的管理入口）外，其余端口不对外暴露。

## 3. 环境与配置管理

### 3.1 `.env.example`

```dotenv
# ---- 应用 ----
APP_ENV=dev
APP_HOST=0.0.0.0
APP_PORT=8000
LOG_LEVEL=INFO

# ---- Milvus ----
MILVUS_HOST=milvus
MILVUS_PORT=19530
MILVUS_COLLECTION=kb_chunks

# ---- Ollama / 生成 ----
OLLAMA_BASE_URL=http://ollama:11434
LLM_MODEL=qwen2.5:7b
EMBEDDING_MODEL=qwen3-embedding

# ---- 检索参数 ----
TOP_N_DENSE=20
TOP_N_SPARSE=20
TOP_N_FUSED=50
TOP_K=5
RRF_K=60
RERANK_ENABLED=false

# ---- 编排 / 会话 ----
CHECKPOINTER_BACKEND=sqlite
CHECKPOINTER_PATH=/data/checkpoints.sqlite
SESSION_TTL_DAYS=7

# ---- 可观测 ----
LANGSMITH_ENABLED=false
LANGSMITH_API_KEY=
LANGSMITH_PROJECT=it-ticket-assistant
LANGSMITH_ENDPOINT=https://api.smith.langchain.com

# ---- 安全 ----
IDEMPOTENCY_TTL_HOURS=24
```

### 3.2 配置规则

- 所有可调参数集中在 `app/core/config.py`，通过 `pydantic-settings` 读取环境变量。
- `.env` 不提交仓库，仅提交 `.env.example`。
- 敏感值（`LANGSMITH_API_KEY` 等）通过环境变量或 secret 注入，禁止写入日志。

### 3.3 环境划分

| 环境 | 用途 | 差异 |
| --- | --- | --- |
| dev | 本地开发 | 小模型、LangSmith 可关、数据可重置 |
| test | 自测/回归 | 独立数据卷、可换小模型加速 |
| prod | 内网生产 | GPU、正式模型、开启观测与备份 |

## 4. 镜像与构建

### 4.1 应用 Dockerfile（多阶段）

```dockerfile
# ---- builder ----
FROM python:3.11-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ---- runtime ----
FROM python:3.11-slim
WORKDIR /app
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
COPY --from=builder /install /usr/local
COPY app ./app
COPY ingestion ./ingestion
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD python -c "import urllib.request;urllib.request.urlopen('http://localhost:8000/api/v1/health')" || exit 1
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

- 基础镜像锁定 `python:3.11-slim`；依赖来自 `requirements.txt`。
- 镜像 tag 记录在 compose 中，避免 `latest` 漂移。

## 5. Docker Compose 编排

```yaml
services:
  api:
    build: .
    env_file: .env
    ports: ["8000:8000"]
    depends_on:
      milvus: { condition: service_healthy }
      ollama: { condition: service_started }
    volumes:
      - checkpoint_data:/data
    restart: unless-stopped

  milvus:
    image: milvusdb/milvus:v2.4.x
    command: ["milvus", "run", "standalone"]
    environment:
      ETCD_ENDPOINTS: etcd:2379
      MINIO_ADDRESS: minio:9000
    ports: ["19530:19530", "9091:9091"]
    depends_on: [etcd, minio]
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9091/healthz"]
      interval: 30s
      timeout: 10s
      retries: 5
    restart: unless-stopped

  etcd:
    image: quay.io/coreos/etcd:v3.5.x
    environment:
      ETCD_AUTO_COMPACTION_MODE: revision
      ETCD_AUTO_COMPACTION_RETENTION: "1000"
    volumes: ["etcd_data:/etcd"]
    restart: unless-stopped

  minio:
    image: minio/minio:latest
    environment:
      MINIO_ROOT_USER: ${MINIO_USER:-minioadmin}
      MINIO_ROOT_PASSWORD: ${MINIO_PASSWORD:-minioadmin}
    command: minio server /data
    volumes: ["minio_data:/data"]
    restart: unless-stopped

  ollama:
    image: ollama/ollama:latest
    ports: ["11434:11434"]
    volumes: ["ollama_data:/root/.ollama"]
    # 有 GPU 时取消注释：
    # deploy: { resources: { reservations: { devices: [{ capabilities: ["gpu"] }] } } }
    restart: unless-stopped

volumes:
  checkpoint_data:
  etcd_data:
  minio_data:
  ollama_data:
```

### 5.1 启动顺序与依赖

1. `etcd`、`minio` 就绪 → `milvus` 健康（`/healthz`）。
2. `ollama` 启动 → 需先 `pull` 模型。
3. `api` 依赖 `milvus` 健康后启动，通过 `/health` 暴露依赖状态。

### 5.2 常用命令（Makefile 封装）

| 命令 | 作用 |
| --- | --- |
| `make up` | 构建并启动全部服务 |
| `make down` | 停止服务（保留数据卷） |
| `make logs` | 跟踪日志 |
| `make pull-model` | `ollama pull qwen2.5:7b` |
| `make ingest` | 导入知识库（执行入库脚本） |
| `make test` | 运行回归测试 |
| `make reset` | 停止并删除数据卷（危险，仅 dev） |

## 6. 数据卷与持久化

| 卷 | 内容 | 重要性 | 备份策略 |
| --- | --- | --- | --- |
| `minio_data` | 知识库向量数据对象 | 高 | 定期快照 + 可重建（有源文档） |
| `etcd_data` | Milvus 元数据 | 中 | 随 minio 一起快照 |
| `ollama_data` | 模型文件 | 低 | 可重新 pull，无需备份 |
| `checkpoint_data` | 会话/审核状态（SQLite） | 高 | 定期备份，含人工审核轨迹 |

- 数据可重建性：知识库可由 `ingestion` 脚本 + 源文档重建；**会话状态不可重建，需备份**。
- 建议备份脚本：`tar` 打包 `checkpoint_data` + `minio_data` 至独立目录/远端。

## 7. 首次启动与初始化

```
1. 复制配置：cp .env.example .env 并填写（如启用 LangSmith）
2. 启动基础服务：make up（优先 etcd/minio/milvus）
3. 拉取模型：make pull-model
4. 验证依赖：curl http://localhost:8000/api/v1/health
5. 导入知识库：make ingest
6. 冒烟验证：提交一条测试工单，确认 SSE 正常返回
```

## 8. 资源与硬件要求

| 场景 | CPU | 内存 | 磁盘 | GPU | 说明 |
| --- | --- | --- | --- | --- | --- |
| 最低（小模型量化） | 4 核 | 16 GB | 30 GB | 无 | 可跑通，生成较慢，适合 Demo |
| 推荐 | 8 核 | 32 GB | 60 GB | 1×GPU(≥8GB) | 体验较好 |
| 生产（内网） | 16 核+ | 64 GB+ | 200 GB+ | 1×GPU(≥16GB) | 并发与稳定性 |

- Milvus 独立模式对内存较敏感，内存不足会显著拖慢检索。
- 磁盘主要为模型文件与向量数据；知识库规模增长时优先扩容磁盘。

## 9. 运维任务

### 9.1 日常监控

| 监控项 | 方式 | 阈值/告警 |
| --- | --- | --- |
| 服务存活 | `/api/v1/health` | 连续失败 3 次告警 |
| 依赖状态 | health 中的 milvus/ollama | 任一 down 告警 |
| 检索延迟 | 应用指标/日志 | 超阈值告警 |
| 首 token 延迟 | 应用指标 | 超阈值告警 |
| 降级次数 | 日志计数 | 频繁降级告警 |
| 审核积压 | 待审核工单数 | 超 SLA 告警 |
| 磁盘/内存 | 主机监控 | 超 85% 告警 |

### 9.2 日志

- 输出到 stdout（容器友好），由 Docker 收集；`LOG_LEVEL` 可调。
- 关键字段：`trace_id`、`ticket_id`、`session_id`、节点名、耗时、降级标记。
- 敏感内容（工单正文）按需脱敏，日志不记录密钥。

### 9.3 备份与恢复

| 项 | 频率 | 方式 |
| --- | --- | --- |
| 会话状态 | 每日 | 打包 `checkpoint_data` |
| 向量数据 | 每周 / 变更后 | 快照 `minio_data` + `etcd_data` |
| 知识库源文档 | 变更时 | 版本化管理（git 或对象存储） |

恢复：停服 → 还原卷 → 启动 → `/health` 校验 → 冒烟测试。

### 9.4 升级与回滚

```
升级：拉取新代码 → 构建镜像(固定 tag) → make down → make up → 健康检查 → 冒烟
回滚：切回上一镜像 tag → make down → make up → 校验
```

- 镜像使用**固定 tag**（不用 `latest`），便于回滚。
- 涉及 Milvus schema 变更时，需评估兼容性（是否需重建 collection）。

## 10. 故障处理 Runbook

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `/health` milvus=down | etcd/minio 未起或端口冲突 | 检查依赖容器日志，重启 milvus |
| 检索返回空 | 索引未加载/数据未导入 | 确认 `make ingest` 已执行、collection 存在 |
| 生成超时 | 模型过大/无 GPU/内存不足 | 换小模型/量化，或增加资源 |
| api 起不来 | 依赖未健康/配置错误 | 看 api 日志，核对 `.env` |
| 审核恢复失败 | Checkpointer 数据异常/会话过期 | 查 `checkpoint_data`，确认未超 TTL |
| 推送/SSE 中断 | 客户端超时/网络 | 客户端重连（预留 `Last-Event-ID`） |
| 磁盘满 | 日志/模型/向量增长 | 清理日志、扩容、归档冷数据 |

## 11. 安全与合规

| 项 | 措施 |
| --- | --- |
| 密钥管理 | 环境变量注入，不入库不入镜像不打日志 |
| 网络暴露 | 仅 `api` 对外；Milvus/Ollama 仅内网 |
| 数据脱敏 | LangSmith 仅上报必要元数据，敏感字段脱敏 |
| 访问控制 | MVP 内网无认证；v1.3 加 Token 鉴权 |
| 审计 | 保留审核操作记录（谁、何时、决定、意见） |
| 依赖安全 | 定期更新镜像与依赖，锁版本 |

## 12. 个人开发的简化实践

| 实践 | 说明 |
| --- | --- |
| 优先 compose，不做 K8s | 单机 compose 足够 MVP，避免过度工程 |
| 监控先看 `/health` | 不引入 Prometheus/Grafana，先靠健康检查 + 日志 |
| 备份用脚本不用平台 | 一个 `backup.sh` 即可，定时任务调用 |
| 模型可重建不备份 | `ollama_data` 不备份，省空间 |
| 固定 tag 保回滚能力 | 成本极低，收益高 |
| 文档即运维手册 | 本文件 + README 就是 Runbook，不另建系统 |
