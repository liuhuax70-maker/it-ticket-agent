# 测试与验收方案

> 文档版本：v1.0
> 文档状态：初稿（待评审）

## 1. 目标与范围

| 目标 | 说明 |
| --- | --- |
| 验证闭环可用 | 工单「接入→检索→生成→审核→发送」端到端跑通 |
| 验证检索有效 | 专有名词类与语义类问题均能命中 |
| 验证安全合规 | 敏感工单强制人工审核，不误发 |
| 验证健壮性 | 依赖不可用/超时/无命中时有明确降级 |
| 量化效果 | 通过 RAGAS 六指标给出可回归的基线 |

范围：MVP（v1.0）功能与非功能测试；RAGAS 完整评估列为 v1.1 强化项，但 MVP 需保留最小评估能力。

## 2. 测试分层与策略

| 层级 | 目的 | 工具 | 覆盖 |
| --- | --- | --- | --- |
| 单元测试 | 验证纯逻辑 | `pytest` | 切分/元数据抽取、RRF、State 路由、错误码映射 |
| 集成测试 | 验证模块协作 | `pytest` + 真实 Milvus/Ollama（或容器） | 检索链、生成链、图执行 |
| 端到端测试 | 验证对外行为 | `httpx` 调 API（含 SSE） | 三条主路径 + 降级 |
| 检索质量评估 | 验证召回 | 最小评估集 + 人工核对 | 专有名词 / 语义 |
| 效果评估（v1.1） | 量化 RAG 质量 | RAGAS | 六指标 |
| 人工验收 | 最终确认 | 手工核对 Checklist | §7 |

个人开发策略：**自动化做「可重复」的部分（单元/集成/评估脚本），人工只做「判断性」的部分（草稿质量、审核体验）**。

## 3. 测试环境

| 项 | 说明 |
| --- | --- |
| 运行方式 | 本地 Docker Compose（api / milvus / etcd / minio / ollama） |
| 依赖版本 | 记录在 `requirements.txt` 与镜像 tag，避免漂移 |
| 数据 | 专用测试知识库（与生产隔离），固定导入脚本 |
| 配置 | `.env.test`，模型可换小模型以加速用例 |
| 网络 | 无外网依赖（全本地），便于离线回归 |

## 4. 测试数据准备

| 数据 | 规模 | 用途 |
| --- | --- | --- |
| 测试知识库 | 手册 3~5 篇 + FAQ 20~30 条 + 历史工单 20~30 条 | 检索与生成 |
| 最小评估集 | 20 条（10 专有名词 + 10 语义） | 召回验证 |
| 参考答案集 | 与评估集配对 | RAGAS（v1.1） |
| 敏感样例 | 若干条含敏感关键词工单 | 审核路径 |
| 无命中样例 | 知识库外问题若干条 | 降级验证 |
| Mock 数据 | 用于单测的固定 Chunk/State | 纯逻辑测试 |

- 评估集需包含**错误码**、**版本号**、**语义化改写**三类，且标注期望命中的 `chunk_id`。

## 5. 用例设计

### 5.1 单元测试

| 编号 | 用例 | 期望 |
| --- | --- | --- |
| U-01 | 文档切分 | chunk 长度在阈值内，重叠正确 |
| U-02 | 元数据抽取 | 正确识别 `v1.2.3`、`ERR-4041` |
| U-03 | RRF 融合 | 给定两路排名，融合排名符合公式 |
| U-04 | 意图路由 | 敏感关键词 → `need_review=True` |
| U-05 | 条件边 | 无命中 → 走 finalize 分支 |
| U-06 | 错误码映射 | 异常 → 对应业务错误码 |
| U-07 | 幂等键 | 同 `ticket_id` 重复送不重复发送 |

### 5.2 集成测试

| 编号 | 用例 | 期望 |
| --- | --- | --- |
| I-01 | 向量入库 + 稠密检索 | 能召回对应片段 |
| I-02 | BM25 检索 | 错误码 query 命中 |
| I-03 | 完整检索链 | 稠密+稀疏+RRF 返回 Top-K |
| I-04 | 生成链 | 流式产出草稿，citations 非空 |
| I-05 | 图执行（普通） | 走到 send，状态落库 |
| I-06 | 图执行（敏感） | 在 review 处 interrupt |
| I-07 | Checkpointer 恢复 | resume 后从 review 继续 |

### 5.3 端到端测试（API）

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| E2E-01 | 普通咨询工单 | SSE 依次收到 start/intent/retrieval/token…/draft/done |
| E2E-02 | 敏感工单 | 收到 `review_required` 后流结束；`/ticket/review` approve 后 `send_status=sent` |
| E2E-03 | 审核 rejected | 不发送，工单状态为 rejected |
| E2E-04 | 无命中 | 返回「未找到」类回复，不臆造，可转人工 |
| E2E-05 | 会话查询 | `/session/{id}` 返回该会话工单与状态 |
| E2E-06 | 健康检查 | `/health` 反映各依赖真实状态 |

### 5.4 检索质量测试

| 编号 | 用例 | 期望 |
| --- | --- | --- |
| Q-01 | 10 条专有名词问题 | 命中率 ≥ 80%，且 Top-5 含正确 `chunk_id` |
| Q-02 | 10 条语义化问题 | 命中率 ≥ 70% |
| Q-03 | 通道对比 | 记录仅稠密 / 仅 BM25 / 混合 三组命中对比 |
| Q-04 | 重排对比（v1.1） | 重排前后 Top-K 准确率提升 |

> 阈值可按实际首轮结果调整，但需在文档中记录最终基线与结论。

### 5.5 非功能测试

| 编号 | 用例 | 期望 |
| --- | --- | --- |
| N-01 | 首 token 延迟 | 在可接受范围（建议 ≤ 5s，视硬件） |
| N-02 | 检索耗时 | 召回+融合 ≤ 500ms；重排 ≤ 800ms |
| N-03 | Milvus 不可用 | 降级 BM25，标记 degraded，不报 500 |
| N-04 | Ollama 不可用 | 失败重试后降级/转人工 |
| N-05 | 重排超时 | 跳过重排仍返回结果 |
| N-06 | 并发（轻量） | 若干并发请求无串话、状态互不污染 |

## 6. RAGAS 评估方案（v1.1 强化）

| 项 | 内容 |
| --- | --- |
| 数据集 | 评估集 + 参考答案 + 检索上下文三元组 |
| 指标 | Faithfulness、Answer Relevancy、Context Precision、Context Recall、Answer Correctness、Context Entities Recall |
| 运行方式 | 离线脚本，输出 JSON/Markdown 报告，可对比历史基线 |
| 通过标准 | 首轮建立基线；后续版本不得低于基线（允许约定容差） |
| 关注重点 | Context Entities Recall（错误码/版本号等实体召回） |

MVP 阶段：先跑 Q-01~Q-03 的召回统计，RAGAS 可延后。

## 7. 验收标准（对齐需求）

### 7.1 功能验收 Checklist

- [ ] 普通工单：SSE 流式返回草稿，内容忠实于检索上下文。
- [ ] 专有名词工单：检索命中对应错误码/版本号片段。
- [ ] 语义化工单：检索命中语义相关知识片段。
- [ ] 敏感工单：触发 interrupt，不直接发送。
- [ ] 审核 approve：恢复执行并成功发送，状态落库。
- [ ] 审核 rejected：流程结束，不发送。
- [ ] 无命中：给出明确「未找到」提示，不臆造。
- [ ] `/session/{id}` 可查询会话状态。
- [ ] `/health` 正确反映依赖状态。

### 7.2 非功能验收 Checklist

- [ ] 首 token 延迟在约定阈值内。
- [ ] 检索耗时在约定阈值内。
- [ ] Milvus 不可用时降级为 BM25 且不返回 500。
- [ ] Ollama 不可用时降级/转人工且行为可预期。
- [ ] 同一 `ticket_id` 不重复发送（幂等）。
- [ ] LangSmith 可查看完整 trace。

### 7.3 部署验收 Checklist

- [ ] `docker-compose up` 一键拉起全部服务。
- [ ] 按 README 可在干净环境复现启动。

## 8. 缺陷分级与处理

| 级别 | 定义 | 处理策略 |
| --- | --- | --- |
| P0 | 闭环不可用 / 敏感工单误发 | 立即修复，阻塞交付 |
| P1 | 主路径功能异常（如无法审核恢复） | 本迭代内修复 |
| P2 | 非主路径问题 / 体验瑕疵 | 排入 v1.1 |
| P3 | 优化建议 | 记录待议 |

个人开发建议：**只对 P0/P1 设门槛，P2/P3 记入 backlog**，避免过度测试拖慢进度。

## 9. 回归策略

- 每次改动检索/编排/接口后，至少回归：U-03、U-05、I-05、I-06、E2E-01、E2E-02。
- 提供一键脚本 `make test` / `pytest -m regression` 跑核心回归集。
- 评估集召回结果存档，版本间对比，防止效果回退。

## 10. 个人开发的简化实践

| 实践 | 说明 |
| --- | --- |
| 优先自动化可重复项 | 单测 + 检索评估脚本，人工只做质量判断 |
| 用最小评估集代替大规模标注 | 20 条起步，逐步扩充 |
| 用固定种子/固定数据 | 保证结果可比、可复现 |
| 小模型加速用例 | 功能用例可用更小模型，效果评估再用正式模型 |
| 一人分角色 | 编码与验收之间留出「冷却期」再自测，减少确认偏差 |
| 记录而非追求完备 | 首轮以建立基线为目标，不做过度测试 |
