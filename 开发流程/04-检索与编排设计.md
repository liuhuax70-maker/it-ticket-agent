## 1. 设计目标与约束

| 目标 | 说明 |
| --- | --- |
| 双通道召回 | 专有名词/错误码/版本号走 BM25，语义提问走向量，两路互补 |
| 融合稳定 | 用 RRF 融合异构分数，无需调权重 |
| 精度可控 | 重排后取 Top-K，兼顾质量与延迟 |
| 状态可恢复 | 编排状态持久化，支持人工审核挂起与多轮续跑 |
| 流式体验 | 草稿生成边生成边回传（SSE） |
| 可观测 | 每次检索与每个节点均可被 LangSmith 追踪 |

约束：
- 向量化与生成均本地（服务化在 Docker 内）。
- 检索延迟目标：召回 + 融合 ≤ 500ms；重排 ≤ 800ms（Top-N=50 → 5）。
- MVP 不强依赖重排（可开关），但接口与流程需预留。

## 2. 检索设计

### 2.1 检索总体流程

```
Query
  │
  ├─► [稠密通道] qwen3-embedding → Milvus ANN 检索 ──► Top-N_dense
  │
  └─► [稀疏通道] Milvus 内置 BM25 检索 ─────────────► Top-N_sparse
                          │
                          ▼
                    [RRF 融合]
                          │
                          ▼
                 [Qwen3-Reranker 重排]（可开关）
                          │
                          ▼
                     Top-K 上下文
```

### 2.2 数据模型与 Milvus Collection Schema

Collection：`kb_chunks`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `pk` | VARCHAR / INT64（主键） | 唯一标识，建议 `{doc_id}#{chunk_id}` |
| `content` | VARCHAR | 切分后的文本片段（BM25 输入） |
| `dense` | FLOAT_VECTOR(dim=D) | qwen3-embedding 向量（D 以实际模型为准，示例 1024） |
| `sparse` | SPARSE_FLOAT_VECTOR | BM25 稀疏向量 |
| `doc_id` | VARCHAR | 文档标识 |
| `source` | VARCHAR | 来源：manual / faq / ticket |
| `title` | VARCHAR | 标题/问题 |
| `version` | VARCHAR | 版本号（可空） |
| `error_code` | VARCHAR | 错误码（可空，用于精确过滤） |
| `updated_at` | INT64 | 更新时间戳 |

索引：
- `dense`：`IVF_FLAT` / `HNSW`，度量 `COSINE`（或 `IP`，与 embedding 归一化策略一致）。
- `sparse`：`SPARSE_INVERTED_INDEX`，度量 `BM25`，配置 `k1`、`b`。
- 标量索引（可选）：`source`、`error_code` 用于过滤。

> Milvus 通过 `Function` 定义 BM25：提供 `content` 与 `sparse` 字段映射，写入时由 Milvus 自动生成稀疏向量。

### 2.3 文档切分与向量化

| 环节 | 策略 |
| --- | --- |
| 切分粒度 | 按标题/段落优先，chunk ≈ 300~500 token，重叠 50 token |
| 元数据提取 | 正则/规则抽取版本号（如 `v1.2.3`）、错误码（如 `ERR-4041`）写入标量字段 |
| 向量化 | 批量调用 qwen3-embedding，归一化后写入 |
| 去重 | 按 `content` 哈希去重，避免重复片段污染召回 |
| 更新 | MVP 手动重跑导入脚本；v1.2 起做增量 |

### 2.4 稠密检索

- 输入：用户 query（可做查询改写/扩展，MVP 先不做）。
- 调用：qwen3-embedding 生成 query 向量 → Milvus ANN 检索。
- 参数：`nprobe` / `ef` 按索引类型设置，召回 `Top-N_dense`（默认 20）。
- 过滤：可带 `source` / `error_code` 等标量过滤条件。

### 2.5 稀疏检索（BM25）

- Milvus 内置 BM25：对 query 分词后生成稀疏向量，与库内稀疏向量做打分。
- 中文分词：引入 `jieba` 自定义分析器（Milvus BM25 支持分词器配置），保证中文与错误码切分合理。
- 参数：`k1`（词频饱和，默认 1.2）、`b`（长度归一，默认 0.75）。
- 召回 `Top-N_sparse`（默认 20）。
- 价值：错误码、版本号、专有名词的精确/近似精确命中。

### 2.6 RRF 融合

Reciprocal Rank Fusion，按排名而非分数融合，避免量纲不一致：

```
RRF_score(d) = Σ_i  1 / (k + rank_i(d))
```

- `k` 默认 **60**；`rank_i(d)` 为文档 d 在第 i 路结果中的排名（从 1 开始）。
- 参与融合的通道：稠密、稀疏（v1.1 可加入更多通道）。
- 融合后取 `Top-N_fused`（默认 50）进入重排。

### 2.7 重排（Qwen3-Reranker，可开关）

- 输入：query + `Top-N_fused` 候选文档。
- 输出：相关性分数重排，取 `Top-K`（默认 5）。
- 开关：`RERANK_ENABLED`（MVP 默认 `false`，v1.1 打开）。
- 延迟控制：`Top-N_fused` 上限 50；可只对前 N 条重排。

### 2.8 检索参数汇总（可配置）

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `TOP_N_DENSE` | 20 | 稠密通道召回数 |
| `TOP_N_SPARSE` | 20 | 稀疏通道召回数 |
| `TOP_N_FUSED` | 50 | 融合后进入重排数 |
| `TOP_K` | 5 | 最终进入生成上下文的片段数 |
| `RRF_K` | 60 | RRF 常数 |
| `RERANK_ENABLED` | false | 是否启用重排 |
| `SCORE_THRESHOLD` | 可空 | 融合后最低分阈值，低于则视为无命中 |

### 2.9 检索失败与降级

| 情况 | 处理 |
| --- | --- |
| 无命中（空结果 / 低于阈值） | 不生成臆造答案，回复「未找到相关知识」并建议转人工 |
| 向量服务不可用 | 降级为仅 BM25 检索，并标记 degraded 状态 |
| BM25 索引不可用 | 降级为仅向量检索 |
| 重排超时 | 跳过重排，直接使用融合结果 |
| 两路均不可用 | 返回错误并转人工，不调用生成 |

## 3. 编排设计（LangGraph）

### 3.1 状态模型（State）

```python
class TicketState(TypedDict):
    # 输入
    session_id: str
    ticket_id: str
    query: str
    history: list[Message]        # 多轮上下文（MVP 可为空）

    # 中间产物
    intent: str                   # consult / sensitive
    need_review: bool             # 是否需人工审核
    retrieved: list[Chunk]        # Top-K 检索结果
    retrieval_debug: dict         # 各路召回/融合/重排信息（用于观测）
    draft: str                    # 草稿
    citations: list[str]          # 引用的 doc_id/chunk_id

    # 审核与发送
    review_status: str            # pending / approved / rejected
    reviewer_comment: str
    reply: str                    # 最终发送内容
    send_status: str              # sent / failed
    error: str
```

> 状态整体由 Checkpointer 持久化，`session_id` + `ticket_id` 作为恢复键。

### 3.2 图节点定义

| 节点 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| `intent_node` | query | 意图识别（MVP：敏感关键词/规则命中即 `sensitive`） | `intent`, `need_review` |
| `retrieve_node` | query | 混合检索（§2 全流程） | `retrieved`, `retrieval_debug` |
| `draft_node` | query, retrieved | 组装 Prompt → Qwen2.5 流式生成 | `draft`, `citations` |
| `review_node` | draft | `interrupt` 挂起，等待人工 | `review_status`, `reviewer_comment` |
| `finalize_node` | draft / review_status | 生成最终回复文本 | `reply` |
| `send_node` | reply | 发送并落库 | `send_status` |

### 3.3 条件路由（边）

```
START → intent_node
intent_node --(need_review=True)--> draft_node
intent_node --(need_review=False)--> retrieve_node

retrieve_node --(有命中)--> draft_node
retrieve_node --(无命中)--> finalize_node   # 走「未找到」回复或转人工

draft_node --> review_node      # 敏感/复杂 → 人工审核
draft_node --> finalize_node    # 普通 → 直接成稿（MVP 可配置是否需要人工确认）

review_node --(approved)--> finalize_node
review_node --(rejected)--> END   # 打回，等待修改后重新提交

finalize_node --> send_node --> END
```

说明：
- MVP 为简化，可将「普通工单」也统一走一次轻量人工确认，再逐步放开自动发送。
- `rejected` 分支结束本轮，人工修改后可重新 `invoke` 恢复。

### 3.4 人工审核：interrupt / resume

- 通过 LangGraph 的 `interrupt()` 在 `review_node` 挂起图执行，等待外部输入。
- 挂起时状态由 Checkpointer 保存，`invoke` 返回中断信息（含 `ticket_id`）。
- 恢复：调用审核接口，用 `Command(resume=...)` 注入审核结果，图从 `review_node` 继续。
- 审核载荷：

```json
{
  "ticket_id": "T-1001",
  "session_id": "S-abc",
  "decision": "approved | rejected",
  "comment": "修改了措辞，补充了 v1.2.3 的说明",
  "edited_reply": "可选，人工修改后的最终文案"
}
```

### 3.5 Checkpointer 与多轮

- 每个 `session_id` 维护一条线程（`thread_id`），状态随节点推进落库。
- MVP 使用本地 SQLite（`langgraph.checkpoint.sqlite`），生产可换 Postgres/Redis。
- 多轮（v1.1）：新 query 与 `history` 一起进入 `intent_node`；如需改写查询，增加 `rewrite_node`。
- 会话 TTL：定期清理过期 thread（默认 7 天，可配置）。

### 3.6 流式输出（SSE）对接

- `/ticket/query` 返回 `text/event-stream`。
- 事件类型：

| event | data | 时机 |
| --- | --- | --- |
| `intent` | `{intent, need_review}` | 意图识别完成 |
| `retrieval` | `{hit_count, top_docs[]}` | 检索完成（可脱敏） |
| `token` | `{delta}` | 草稿逐 token 流式 |
| `draft` | `{draft, citations}` | 草稿完成 |
| `review_required` | `{ticket_id, reason}` | 触发人工审核 |
| `done` | `{reply, send_status}` | 流程结束 |
| `error` | `{code, message}` | 异常 |

- 实现：`draft_node` 内使用 Qwen2.5 流式接口，边生成边 `yield` token。
- 前端在收到 `review_required` 后断开流，待审核通过另行拉取结果。

### 3.7 错误处理、重试与超时

| 项 | 策略 |
| --- | --- |
| 节点异常 | 捕获后写入 `state.error`，路由到 `error` 终点，不中断整个服务 |
| LLM 调用失败 | 指数退避重试（默认 2 次），仍失败则降级为「模板 + 检索片段」回复或转人工 |
| 检索超时 | 单通道超时（默认 2s）降级为另一通道 |
| 幂等 | `send_node` 以 `ticket_id` 幂等，避免重复发送 |
| 审核超时 | 超过 SLA 未审核则提醒（v1.2） |

## 4. 接口契约（与检索/编排相关）

| 接口 | 方法 | 说明 |
| --- | --- | --- |
| `/ticket/query` | POST (SSE) | 提交工单，流式返回，敏感时中断并返回 `review_required` |
| `/ticket/review` | POST | 提交审核结果，恢复图执行 |
| `/session/{session_id}` | GET | 查询会话状态与历史 |
| `/health` | GET | 健康检查（Milvus / Ollama 连通性） |

请求体核心字段：`session_id`、`ticket_id`、`query`、`source`（员工/客户）。

## 5. 可观测埋点

- 每个节点设置 LangSmith run name（`intent` / `retrieve` / `draft` / `review` / `send`）。
- `retrieval_debug` 记录：各通道召回数、RRF 融合 Top 排行、重排前后顺序、最终 Top-K。
- 关键指标：检索命中率、无命中率、降级次数、审核触发率、重排耗时、首 token 延迟。
- 敏感字段（工单正文）按需脱敏后再上报。

## 6. 测试与验收

| 用例 | 期望 |
| --- | --- |
| 含错误码 query | BM25 通道命中对应片段，最终上下文含该错误码 |
| 语义化 query | 稠密通道命中语义相关知识 |
| 无相关知识 query | 返回「未找到」，不臆造 |
| 敏感工单 | 触发 `interrupt`，SSE 返回 `review_required` |
| 审核 approve | 恢复执行并发送成功 |
| 审核 reject | 流程结束，不发送 |
| 向量服务不可用 | 降级为 BM25，标记 degraded |
| 重排超时 | 跳过重排仍返回结果 |
| 多轮追问（v1.1） | 能结合 history 正确回答 |
