# ADR 0006：查询缓存键必须包含身份维度

- 状态：已采纳
- 日期：2026-10-07

## 背景：一条被配置掩盖的越权路径

做评测时发现查询缓存的键是：

```python
f"{tenant_id}|{mode}|{top_k}|{normalize(query)}"
```

**不含部门与用户。** 于是在同一租户内：

1. alice（hr 部门）问「招聘需求审批中，编制核对需要在几个工作日内完成？」→ 正常检索到
   《人力资源部内部制度》，答案与引用被写入缓存；
2. bob（engineering 部门）问**字面完全相同**的问题 → 缓存命中，直接拿到 alice 那条答案；
3. bob 的响应里带着他**无权查看**的 HR 文档引用。

检索层的 ACL 过滤被整段绕过——`retrieval` 根本没有被调用。
本项目的评测集里恰好有一组这样的"权限切片"（同一问题、不同身份、期望相反），
只要缓存是开的，它就会直接命中。

## 为什么此前全绿

`.env` 里 `CACHE_ENABLED=false`。权限验收（S7）、端到端验收、评测基线全部在缓存关闭
的状态下跑过，无一失败。

这是最危险的一类缺陷：**只在生产配置下存在**。默认关闭的开关把问题藏了起来，
而不是暴露它。

## 决策

缓存键改为：

```
(tenant_id, department_id, user_id, mode, top_k, temperature, normalize(query))
```

- **按用户而非按部门隔离**：文档可见性有 `private` 一档，按 owner 过滤，
  同部门内不同人仍然必须分开。
- **temperature 也要进键**：温度不同则答案不同。评测固定温度 0 时，
  若与默认温度共用一条缓存，就会把上一轮的结果当成本轮的结果。
- **仍然不缓存拒答**（沿用原决策）：否则"资料缺失"会被固化，文档补录后仍继续吐旧答案。

代价是命中率明显下降——同部门不同人不再共享缓存条目。这个代价接受：
正确性优先。命中率优化（例如只对 `visibility=public` 的语料启用跨用户共享）
留待后续，且必须做成显式配置项而不是默认行为。

## 配套动作

- 新增 7 条回归测试（`services/query-orchestrator/tests/test_cache.py`），
  逐条钉住"改任一维度都必须换键"，防止后续重构再把它删掉。
- 本地 `.env` 打开 `CACHE_ENABLED=true`，并在打开缓存的状态下重跑权限验收与评测，
  让这类缺陷以后能被常规验收发现，而不是靠人读代码。
- 全仓排查了其他 Redis 键：限流与配额按租户（设计如此），
  embedding 缓存按文本派生（结果与身份无关），都不含答案，语义上安全。
