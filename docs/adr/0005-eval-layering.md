# ADR 0005：评测分两层，确定性指标（L1）优先于 LLM 裁判（L2）

- 状态：已采纳
- 日期：2026-10-07

## 背景

评测最初只做了 RAGAS：采集答案 → 交给裁判模型打分。真跑起来暴露四个问题：

1. **慢**：本地裁判（4B，CPU）每个样本要发多次请求，实测三个指标约 56s/样本，
   12 条样本要 11 分钟。这种延迟下没人愿意在改一次切分参数后重跑。
2. **不稳**：LLM 裁判有随机性，同一次改动的前后对比可能被噪声淹没。
3. **不可定位**：分数从 0.82 掉到 0.78，无法回答"是哪几条样本、丢在检索还是生成"。
4. **脆弱**：没装 ragas 就一条指标都产不出来——连"检索到底命没命中"这种
   可判定的事实也拿不到。

而对本项目来说，最该被持续盯住的东西（**越权泄露**、**该拒答有没有拒答**、
**该命中的文档有没有命中**）恰恰都是**可判定的布尔事实**，根本不需要 LLM 裁判。

## 决策

### 1. 评测拆两层

| 层 | 指标 | 是否需 LLM | 定位 |
| --- | --- | --- | --- |
| **L1 确定性** | hit@k、MRR、片段召回、引用覆盖率、拒答准确率、漏答率、误答率、**越权泄露数** | 否 | 每次改动都跑 |
| **L2 RAGAS** | faithfulness、context_precision、context_recall | 是 | 阶段性跑，样本取子集 |

### 2. L1 先算完、先落盘，L2 失败不吃掉 L1

`runner.run()` 的顺序固定为「前置检查 → 采集 → L1 → 可选 L2」，L2 异常被捕获后
只记录错误信息。理由：基线必须在裁判模型不可用时也能产出。

### 3. 指标必须能定位到样本

报告里除了分数，还带 `failures` 明细（`retrieval_miss` / `false_refusal` /
`false_answer` / `error`），每条说清"期望什么、实际引用了什么"。

### 4. 小样本必须显式表达不确定性

hit@k 给 **Wilson 95% 区间**，样本数 < 30 时在报告里写明"请勿据小差异下结论"。
41 条样本下 3% 的差异完全可能是噪声，这个提示比多三个小数位有用。

### 5. 权限维度进评测集

样本带**身份画像**（Keycloak 用户名 + 租户 + 部门）；同一问题在不同身份下期望相反
（有权限→作答，无权限→拒答）。越权禁止集合按两条来：

- 数据集里**显式声明**的 `forbidden_sources`；
- 采集时按台账里**真实 ACL 推导**：租户不符、部门不符一律计入；
  private 文档的 owner 不在台账里，因此采取保守规则——除非样本显式把它写进
  `expected_sources`，否则一律视为不可见。

只靠手写声明会漏检，只靠自动推导会漏掉 private，两者都要。

### 6. 裁判复用项目自己的 LLMClient

RAGAS 的两条现成路径都不合适：`llm_factory`（OpenAI 兼容）关不掉本地思考型模型的
思维链，会拿到空输出、指标全 NaN；`langchain-ollama` 能关但要多引一套依赖，
且模型解析会和项目里的双模解析分裂成两份。

因此用 `app/judge.py:ProjectLLMJudge` 实现 `BaseRagasLLM`，复用 `LLMClient`：
本地端点已经是 `LOCAL_LLM_API_STYLE=ollama` + `LOCAL_LLM_THINK=false`，切 DeepSeek
官方 API 时同一份代码不用改。`is_finished` 判空返回 False，让 RAGAS 抛
`LLMDidNotFinishException`——宁可响亮失败，也不要静默产出一堆 NaN。

### 7. 负样本不参与 L2

拒答文本与上下文无关是**应该的**，拿它算 faithfulness 只会得到无意义的低分。

## 代价与后续

- L1 的"命中"以 **doc_id** 判定，需要维护来源路径 → doc_id 的解析。
  这里踩过一个坑：**通过上传接口入库的文件，其 `source` 会被改写成
  `data/uploads/<文件名>`**，与评测集里写的语料夹具路径不一致。因此解析规则是
  「完整路径精确匹配优先，否则按文件名唯一匹配」，同名多份时直接报错要求写全路径
  （猜错一条来源，越权断言就会静默失效）。
- 依赖锁定：`langchain-community` 必须 `<0.4`。ragas 0.4.3（当前最新）会 import
  `langchain_community.chat_models.vertexai`，该模块在 0.4 已删除，装成 0.4 会让
  `import ragas` 直接失败。这是上游 bug，升级 ragas 时要一并复核。
- L2 仍使用 ragas 的**经典指标**（`ragas.metrics`）而非 `collections`：
  collections 只接受 instructor 结构化输出的 `InstructorLLM`，与上面的裁判适配器
  不兼容。升级到 ragas 1.0 前需要把裁判改写成结构化输出。
- **RAGAS 默认 `RunConfig.timeout=180s` 会让本地裁判整批超时。**
  首轮基线里 `context_precision` 全是 NaN，日志深处是
  `ragas.executor ... TimeoutError()`：这个指标要对**每一条召回上下文分别调用裁判**
  （5 条 × 12 样本 × 多次请求），本地 4B 模型排队就超预算。
  症状极具迷惑性——看起来像"裁判不会解析模型输出"，实际是**没给够时间**。
  处理：`judge_timeout`（默认 900s）与 `judge_workers`（默认 4）可配置，
  并在指标全 NaN 时打警告，而不是让 `null` 悄悄躺在报告里。
  放宽后同一批采集结果重打分：`faithfulness 0.72 → 0.80`，
  `context_precision null → 0.794`，`context_recall 1.0`。
- **4B 本地模型当裁判会有一部分样本解析失败。** 日志里可见
  `OUTPUT_PARSING_FAILURE`：模型确实按格式返回了 `{'statements': [...], 'verdict': 1}`，
  但 langchain 的解析链要求 `StringIO.text`，于是该样本判为失败（`raise_exceptions=False`
  下静默变成 NaN 参与平均）。结论：**本地小模型只够验证链路，不够当可信基准**。
  正式基线应把裁判切到 DeepSeek（改 `LLM_PROVIDER` / `JUDGE_MODEL` 即可，代码无需改动），
  并在报告里记录 `judge_model` 以便区分"模型变了"与"系统变差"。
- 采集与打分是两段：`POST /eval/score`（`make eval-rescore`）读已落盘的
  `baseline_latest.json` 直接重算 L1 + L2。调整裁判模型、指标集合或超时策略时
  不必重新打一遍真实链路（十几分钟起步）。L1 是从保存的行**重算**的，
  不信任报告里缓存的聚合值——行才是权威，缓存值可能来自旧版指标实现。
  实测重打分得到的 L1 与原跑逐位一致，说明这条路径可信。
- 下一步：把 L1 接进 CI 做回归门禁（hit@k 不许下降、越权必须为 0），
  并接入自建 embedding 以启用 answer_relevancy。

## 已知局限（实测发现，记录在案）

**拒答类指标在本地小模型上不稳定，而且原因不是温度。**
同一份评测集在 `LLM_TEMPERATURE=0.2` 下连跑两次，误答率 22.2% → 44.4%，
起初判断是"温度让拒答判断对采样敏感"。于是把 `temperature` 从 `/chat` 透传到
model-gateway（与 ADR 0006 同批改动），评测固定 `temperature=0` 再跑：

| 配置 | 误答率 | MRR | 越权 |
| --- | --- | --- | --- |
| 温度 0.2（第 1 次） | 22.2% | 1.000 | 0 |
| 温度 0.2（第 2 次） | 44.4% | 0.984 | 0 |
| **温度 0** | **44.4%** | 1.000 | 0 |

固定温度**没有**让误答率下降，所以先前那个"温度导致不稳定"的判断是错的。
温度透传这件事本身是对的（消除了一个真实存在的混杂因素，也让缓存键正确），
但**拒答失败的根因是模型能力**：4B 模型会为"帮我写一首关于加班的诗"这类
与上下文无关的问题硬凑引用，而不是说"资料里没有"。

因此：
- 报告里的**漏答率/误答率**要按"同一配置连跑 2~3 次看区间"来读，单次数字不要下结论；
- **越权泄露不受影响**——它由存储层过滤决定，与模型采样无关，所以能当绝对不变量；
- 想真正改善拒答，要换更强的作答模型（本项目的目标配置就是 DeepSeek），
  或在提示词层强化拒答，而不是继续调温度。在换模型之前，
  "拒答率提升"这类改动无法被可信地度量——否则很容易把 4B 模型的噪声当成成果。

### 实测：换成 DeepSeek 之后（2026-10-07）

上面那条"换模型才能可信度量"的判断，已用模型替换**验证**。
配置只改了两个环境变量（`LLM_PROVIDER=deepseek`、`JUDGE_MODEL=deepseek`），
代码一行未改：

| 指标 | 本地 4B | DeepSeek | 说明 |
| --- | --- | --- | --- |
| 误答率 | 44.4%（4/9） | **11.1%（1/9）** | 剩余那条是"写一首诗"的任务边界问题 |
| MRR | 1.000 | 0.9844 | **略降**：引用排序由生成侧决定，与检索质量无关 |
| hit@k / 漏答 / 越权 | 100% / 0% / 0 | 100% / 0% / 0 | 不变量未受影响 |
| P50 / P95 | 3568 / 4720 ms | **1646 / 2384 ms** | 稳态约 0.6s/次，本地 4B 约 3.5s |
| faithfulness | 0.80 | **0.879** | |
| context_precision | 0.794 | **0.958** | |
| context_recall | 1.0 | 1.0 | 已贴顶 |

三点必须一起记住，否则会误读这组数字：

1. **不能宣称统计显著。** 9 条负样本下两个区间是重叠的
   （44.4% 的 CI 是 [0.189, 0.733]，11.1% 是 [0.020, 0.435]）。
   方向明确且机制清楚（失败原因从"硬凑引用"变成"任务边界"），
   但要让误答率**可判定**，负样本需扩到 30 条以上。
2. **MRR 下降不是退化。** 命中任何一条期望来源都计 1，排名取自
   **citations 的顺序**——那是生成侧的选择，不是检索侧的名次。
   想度量检索排序应看片段召回或直接记录检索返回的 doc 顺序。
   （**已落实**：见下方「补记：检索侧排序指标」。现在 `MRR(检索侧)` 与
   `NDCG@5` 量的是真实名次，原来的 `MRR` 保留但标注为「引用序」。）
3. **端点实际服务的模型名与配置名不一致。** 请求 `deepseek/deepseek-chat`，
   响应里报的是 `deepseek-flash`。报告因此同时记录 `judge_model`（请求名）
   与 `judge_served_model`（实际服务名）、以及 `answer_model`——
   否则"分数变了是系统变差还是模型换了一个"无法回答。
   切换模型时还要调大 `CACHE_VERSION`（编排层的缓存键无法感知下游模型变化），
   本次即用 `CACHE_VERSION=1→2` 让 4B 的旧答案立刻失效。

## 补记（2026-10-08）：检索侧排序指标——把「引用序」与「检索序」分开

上面第 2 点指出的问题当时只是记下来，这次解决了。动机不是「补齐一个指标」，
而是**已有的 `MRR` 在名字上骗人**：它在 IR 里约定俗成地指检索排序的名次，
而这里算的是引用顺序，于是「MRR 下降」会被读成「检索变差」——我自己就读错过一次。

### 数据来源必须分开

| 指标 | 数据来源 | 实际量的是 |
| --- | --- | --- |
| `hit@k` / `MRR`（引用序） | `citations` 顺序 | 生成侧：模型挑了哪些引用、按什么顺序排 |
| `MRR`（检索侧）/ `NDCG@5` | 响应 `contexts` 顺序 | 检索侧：RRF 融合 / 重排后的真实名次 |

采集器新增两个字段：`retrieved_doc_ids`（检索侧 doc 名次，去重保序）与
`chunk_doc_ids`（分块→文档归属，与 `contexts` 等长同序）。

**刻意不做引用兜底。** 原先 `contexts` 缺失时会用 `citations` 的片段兜底（为了片段召回）；
若把兜底也用在 `retrieved_doc_ids` 上，缓存命中的行就会带着「生成侧顺序」进入检索侧指标，
缓存越多指标越好看。宁可把它排除出分母，并在报告 `notes` 里写明排除了几条。

### 分级相关性，而不是二值

等级：`0` 不相关 / `2` 期望文档但召回的分块里没有答案原文 / `3` 期望文档且分块里有答案原文。
指数增益 `2^rel - 1`。

二值 NDCG 说不清一件事：**检索到对的文档但切错分块**，和**文档都不对**，
在「命中=1、没命中=0」下都是 0。前者是切分/融合的问题，后者是召回的问题，
修复动作完全不同。分级之后 NDCG 能把二者分开。

### 一个我写错、并被测试抓住的结论

我在指标文档里写过「单个期望文档时 NDCG@k 退化成 MRR@k」——**这是错的**。
DCG 用对数折线 `1/log2(i+2)`，MRR 用线性折线 `1/(i+1)`，只在第 1 名相等：

| 名次 | NDCG@5 | MRR |
| --- | --- | --- |
| 1 | 1.000 | 1.000 |
| 2 | 0.631 | 0.500 |
| 3 | 0.500 | 0.333 |
| 5 | 0.387 | 0.200 |

所以 **NDCG 与 MRR 不可直接比大小**。现在这条关系由
`test_ndcg_is_not_mrr_except_at_first_rank` 钉住，指标文档里也标了警告。
写指标文档时把两个公式的折线关系算一遍只需要一分钟——我漏了这一步。

### 顺带发现：缓存会改变可测量的东西

加 NDCG 时撞到：`retrieved_doc_ids` 的分母是「有检索名次的样本数」，
而**缓存命中的响应里没有 contexts**。于是缓存状态一变，NDCG 的分母就变，
两轮数字不可比；而评测若允许写缓存，还会把评测流量灌进生产缓存，让下一轮拿到一堆命中。
实测：加开关前一轮 55 条里 35 条是命中，延迟虚低到 973 ms（真实未命中约 1.7 s）。

因此给 `ChatRequest` 加了 `use_cache`（默认 `true`，生产行为不变），评测固定传 `false`，
且 `cache_lookup` 与 `cache_store` **都**读它——只挡读不挡写仍会污染缓存。

### 与陈旧进程的又一次相遇

加完指标后第一轮评测跑出来的报告里**根本没有 NDCG 字段**。查下来是
`eval` 服务进程启动于 23:09，而我改指标是在 01:10 之后：
`pipelines/eval_dag/run.py` 只是 `http://localhost:8006` 的 HTTP 客户端，
**指标代码在那个长驻服务里**。重启后同一份代码立刻产出
`NDCG@5 = 0.9891` / `MRR(检索侧) = 0.9853`。

这是本项目第二次被陈旧进程误导（第一次是 `retrieval` 的 `rerank_enabled`：
health 报 `True` 而配置是 `false`）。两次都是同一个形态：
**读运行中服务的状态 ≠ 读仓库配置**——配置在启动时读一次，之后没有漂移检测。

### 补记：L2 的假阴性，以及一处必须收回的结论

补上 `per_sample_by_id`（带样本 id 的逐样本明细）之后，第一次**看清了 L2 到底在打什么分**。
12 条抽样里有 3 条分数低，逐条核对后：**答案完全正确，裁判打错了**。

| 样本 | 答案 | 上下文依据 | 裁判给分 |
| --- | --- | --- | --- |
| `distract-02` | 部门负责人与人力资源部共同审批 | [1]「三千元（含）以上的，须由部门负责人与人力资源部共同审批」**逐字一致** | 0.250 |
| `lifecycle-01` | 一线城市每晚不超过 500 元 | [1]「一线城市每晚不超过**五百元**」 | 0.333 |
| `perm-eng-allowed` | P1 告警需在五分钟内响应 | [1]「P1 告警五分钟内响应」**逐字一致** | 0.500 |

`lifecycle-01` 还暴露出一个具体成因：**语料用中文数字（五百元），答案写成阿拉伯数字（500元）**。
裁判按字符串匹配找依据时就"找不到"，于是判成无依据。这是评测层的**假阴性**——
它把"模型说得对"报成"模型编造了"，方向完全相反。

### 追修（同日晚些时候）：上面的诊断只对了一小部分

先给 NLI 判据注入了"中文数字/格式等价"规则，重打分——**三条分数纹丝不动**。
数字写法差异只解释 `lifecycle-01` 一条。要看到真凶，得拿到裁判的**中间产物**
（它把答案拆成了哪些 statement、每条判 0 的理由），而 `to_pandas()` 不给这些；
最后是绕过 `evaluate()` 直接调 `_create_statements` / `_create_verdicts` 才看到：

| 样本 | 裁判拆出的致命 statements | 真根因 |
| --- | --- | --- |
| `distract-02` | ①「费用超过三千元」②「须由部门负责人审批」③「须由人力资源部审批」④「A 与 B 共同审批」 | ①是**问题里的前提**（上下文当然不会断言某笔具体费用）；②③是把完整主张拆成的**碎片**，单独看都不成立 |
| `lifecycle-01` | ①「按**2024版**差旅费标准…」②③ | 「2024版」来自**问题**，不在上下文里 |
| `perm-eng-allowed` | ②「响应时间要求来源于引用 [1]」 | **引用标记 [1] 被当成内容**，上下文里没有"[1]"这个字符串 |

三种坏法全在**拆分层**，不在 NLI 判据层——改判据当然无效。

修法（两层）：

1. **引用标记确定性剥离**（`_to_ragas_rows`）：`[1][2]` 是我们自己的引用语法，
   裁判不需要它；用提示词让模型"别管引用标记"远不如直接删掉可靠。
2. **拆分器规则**（追加进 `statement_generator_prompt`）：不要把问题的前提带进
   statement；每条 statement 必须是完整自足的主张，禁止把"A 与 B 共同审批"
   拆成"A 审批" + "B 审批"这种单独看即为假的碎片。

实测（同 12 条抽样）：faithfulness **0.7986 → 1.0，12/12 全部满分**，
且 `lifecycle-01` 的判定理由里能看到等价规则在工作（「五百元 is equivalent…」）。

两个方法论教训：

- **诊断错了层，修得再对也没用。** 第一轮我修的是"数字等价"（NLI 层），
  因为它最容易想到；注入规则后分数纹丝不动，反而证明诊断错了。
  区分"假设成立"与"假设未被证伪"的唯一办法，是让被测对象**可观测**——
  拿不到中间产物时，绕过封装直接调内部步骤也是值得的。
- **拆分器的质量决定 faithfulness 的上限。** 逐条 claim 的指标，
  前置的"claim 从哪来"比"claim 怎么判"更容易出错，而且错得更隐蔽：
  判错了还能从 reason 里看出来，拆坏了只会得到一个合理-looking 的低分。

**必须收回的一个结论**：本文开头那张表把"换 DeepSeek 后 faithfulness 0.80 → 0.879"
写成三项 L2 全面提升的一部分。同一份答案、同一裁判（temperature=0）连打 5 次，
faithfulness 落在 **0.788 ~ 0.840（极差 0.052）**；而 0.80 与 0.879 之间的差距与这个噪声量级
相当。**那次"L2 改善"里有多少是裁判噪声，现有数据无法区分。**
能确定归因的只有 L1 那几项（误答率 44.4% → 11.1%、延迟减半），
它们是确定性指标，不受裁判影响。

### 门禁容差因此改为实测值

L2 的门禁容差原设为 0.05，**比实测裁判噪声（极差 0.052）还小**——
同一份代码有时过有时不过。已改为 0.10 并加测试
`test_l2_tolerance_stays_above_measured_judge_noise`，让"调回 0.05"变成一次显式失败。
理由和这个项目的另一条一致：**随机误报的门禁比没有门禁更糟**，人会学会给它加 `|| true`。

同时明确 L2 是**弱信号**：真正的门禁是 L1 与那些硬不变量（越权 0、禁用内容 0）。
（追修之后 faithfulness 已到 1.0，"弱信号"的结论仍然成立——单轮 1.0 不能证明
裁判可靠，只能证明这 12 条不再有可观测的假阴性；裁判噪声依旧存在。）

### 方法教训

这三个假阴性是**靠加了一个字段才发现的**：`per_sample` 里有分数但没有样本 id，
所以之前只能看到一个"0.79"然后猜。给指标加上"哪一条"和"为什么"，
比再加十个聚合数字有用得多。
