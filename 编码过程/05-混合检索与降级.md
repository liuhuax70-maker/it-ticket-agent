## 1. 在整体布局中的位置（从底层到总体）

本次是**检索层的收口**：把前一步落地的两条独立通道组装成一个统一入口。

```
第 4 层  编排        app/graph/nodes/retrieve.py   ← 下一步：调用 hybrid_search
                                  │
第 3 层  检索能力      app/retrieval/hybrid.py      ← 本次：统一入口 + 降级编排
                              ├── dense.search_dense    （稠密通道，已完成）
                              ├── sparse.search_sparse  （BM25 通道，已完成）
                              ├── fuse.reciprocal_rank_fusion （RRF，已完成）
                              └── rerank.rerank         （重排，仍为占位 → 本次按「失败即跳过」处理）
第 2 层  契约与配置    app/core/config.py            ← 本次：新增 channel_timeout_seconds
第 1 层  运行时        Milvus + Ollama
```

- **依赖谁**：两个通道 + 融合 + 可选重排 + 配置。
- **被谁依赖**：`graph/nodes/retrieve.py` 与 `api/retrieval.py`（调试接口）都只调这一个函数。
- **为什么要有它**：把「用哪条通道、怎么合并、出错怎么办」这组决策**收敛到一个地方**，上层不必关心降级细节。

**技术栈：** Python `concurrent.futures.ThreadPoolExecutor`（并行 + 超时）· RRF 融合 · pymilvus · Ollama

## 4. 功能逻辑（按跳转解释）

### 4.1 总流程

**触发点**：`hybrid_search(query, top_k, ...)`（图节点或调试接口调用）

```
hybrid_search()
   │
   ├─ ① 解析参数：未传则取配置（top_k / top_n_dense / top_n_sparse / top_n_fused / rerank_enabled）
   │
   ├─ ② 两路并行召回（ThreadPoolExecutor，各自带超时）
   │        ├─ dense.search_dense  ──成功──► dense_chunks     ┐
   │        └─ sparse.search_sparse ─成功──► sparse_chunks    │
   │              失败/超时 ──► [] + 错误原因                   │
   │                                                          ▼
   ├─ ③ 模式判定：hybrid / dense_only / sparse_only / degraded
   │        └─ degraded ──► 直接返回空结果（建议转人工）
   │
   ├─ ④ 融合
   │        ├─ hybrid      ──► reciprocal_rank_fusion([dense, sparse])
   │        ├─ dense_only  ──► dense_chunks[:top_n_fused]
   │        └─ sparse_only ──► sparse_chunks[:top_n_fused]
   │
   ├─ ⑤ 可选重排（rerank_enabled 且融合非空）
   │        └─ 抛错/未实现 ──► 记日志并跳过，沿用融合结果（reranked=False）
   │
   └─ ⑥ 截断 top_k，返回 (final, mode, debug)
```

**技术栈：** Python 函数编排 · `ThreadPoolExecutor` · RRF

### 4.2 并行召回与超时降级

**触发点**：进入 ② 时。

```
with ThreadPoolExecutor(max_workers=2):
    dense_future  = submit(search_dense,  query, top_n_dense,  filters)
    sparse_future = submit(search_sparse, query, top_n_sparse, filters)

    _collect(dense_future,  timeout) ─┬─ 正常返回 ──► (chunks, None)
    _collect(sparse_future, timeout) ─┼─ 超时 ─────► ([], "timeout")
                                      └─ 抛异常 ───► ([], "类型: 消息")
```

- **并行**：两路无依赖，串行会白白叠加延迟（稠密还包含一次 embedding 调用）。
- **超时即降级**：`future.result(timeout=...)` 到期就放弃等待，记 `"timeout"`，另一路照常返回。
- **注意**：`future.cancel()` 只能取消**尚未开始**的任务；已在执行的线程无法强杀，这里选择「不再等待」，让它自行结束。

**技术栈：** `concurrent.futures`（`ThreadPoolExecutor` / `TimeoutError`）

### 4.3 模式判定

**触发点**：两路结果收集完毕后。

```
dense_error?  sparse_error?   →   mode            →  行为
   否            否                hybrid            两路融合
   是            否                sparse_only       仅 BM25
   否            是                dense_only        仅向量
   是            是                degraded          返回 []，上层转人工
```

**技术栈：** Python 枚举 `RetrievalMode`（来自 `schemas/retrieval.py`，与 API 契约共用）

### 4.4 融合（含分数保留增强）

**触发点**：mode 为 `hybrid` 时。

```
reciprocal_rank_fusion([dense_chunks, sparse_chunks], k=60, top_n=50)
   ├─ 对每路按位置取 rank（从 1 起）
   ├─ score[d] += 1 / (k + rank)
   └─ 同一 chunk_id 在多路出现时（本次增强）：
         dense_score  = 保留非空的那一路
         sparse_score = 保留非空的那一路
         └─► 便于观测「这条结果是谁贡献的」
```

**技术栈：** Python `defaultdict` · Pydantic `model_copy(update=...)`

### 4.5 重排开关与容错

**触发点**：`rerank_enabled=True` 且融合结果非空时。

```
rerank.rerank(query, fused, top_k)
   ├─ 成功 ──────────► reranked=True，用重排后的顺序
   ├─ NotImplementedError ─► 记日志跳过（当前 rerank 仍是占位）
   └─ 其他异常 ────────► 记日志跳过
        └─► 两种情况都沿用融合结果，不影响召回可用性
```

- 设计取舍：重排是**精度增强**而非**可用性前提**，因此失败必须软着陆。

**技术栈：** Python 异常分支 + 日志

### 4.6 调试图信息

**触发点**：每次调用返回时。

```
debug = {
    "mode": "hybrid",              # 实际生效模式
    "dense_hits": 15,              # 各通道命中数
    "sparse_hits": 4,
    "fused": 15,
    "reranked": False,
    "dense_error": None,           # 降级原因（供排障/观测）
    "sparse_error": None,
    "top": [ {chunk_id, rank, rrf_score, dense_score, sparse_score, rerank_score}, ... ],
}
```

- 该结构直接对应 `开发流程/04` §5 的「可观测埋点」，后续会写入图状态 `retrieval_debug` 并上报 LangSmith。

**技术栈：** Python dict → 后续序列化为 JSON 上报

## 5. 关键实现说明

| 项 | 说明 |
| --- | --- |
| **降级矩阵先行** | 先把「两路任意组合」的 4 种情况写成显式模式，再实现行为，避免散落的 if |
| **超时值偏离设计** | 设计文档写 2s，实际默认 **5.0s**：本地 embedding 首次调用含模型加载，2s 会误伤稠密通道；该值已配置化便于调整 |
| **异常吞并是有意为之** | `_collect` 捕获 `Exception` 并标注 `noqa`，因为「降级」本身就是需求；但错误原因全部记入 `debug` 与日志，不静默 |
| **空结果不等于错误** | 两路都成功但无命中时，mode 仍是 `hybrid`，返回 `[]`；语义是「知识库里确实没有」，上层应回「未找到」而非报错 |
| **重排失败不降级 mode** | 重排失败只影响 `reranked` 标志，不改变 `mode`，避免干扰「通道是否可用」的语义 |

## 8. 待办 / 注意

- [ ] **`rerank.py` 仍是占位**：`RERANK_ENABLED=true` 时目前只会打日志跳过；重排是下一个节点。
- [ ] **未实现分数阈值**：设计文档的 `SCORE_THRESHOLD`（低于阈值视为无命中）尚未落地，当前「无命中」只判断结果是否为空。
- [ ] **并行度固定为 2**：目前硬编码 `max_workers=2`；若未来加入更多通道（如按 `error_code` 精确匹配的第三通道）需一并调整。
- [ ] **超时线程无法真正终止**：Python 线程不可强杀，超时后后台线程仍会跑完（占用连接），高并发下需评估连接池压力。
- [ ] **knowledge_base 只有 15 个片段**：导致 `top_n` 常大于实际数据量，各通道都返回全量，RRF 区分度不明显；需扩充知识库后再评估融合效果。
- [ ] `debug["top"]` 目前包含完整 `chunk_id`，上报 LangSmith 时需按脱敏策略过滤。
