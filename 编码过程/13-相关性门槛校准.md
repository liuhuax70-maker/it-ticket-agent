## 1. 在整体布局中的位置（从底层到总体）

本节点给检索层补上**最后一块缺失的判断力**：从「总能召回 8 条」变成「能说不知道」。

```
第 4 层  编排     无命中分支（复用已有路径）→ 转人工
                      ↑
第 3 层  检索     hybrid_search()
                      └─ ★ 新增：相关性门槛（第 6 步）
                           判「无可用资料」→ 返回空 → 上层给 NOT_FOUND_REPLY
──────────── 横向 ────────────
      evaluation/
        ├── calibrate_threshold.py   ← 新增：校准阈值
        └── run_retrieval_eval       ← 新增：报告门槛拦截率
```

- **依赖谁**：200 条评估集（12 篇的成果）+ 稠密通道。
- **被谁依赖**：编排层的「无命中 → 转人工」分支、生成层（少一次无效生成）。
- **为什么要有它**：此前**任何问题都会返回 8 条片段**，负样本 100% 拿到无关片段，
  「该不该拒答」全靠生成层兜底。

**技术栈：** 稠密余弦相似度（Milvus COSINE）· 5 折交叉验证 · 混淆矩阵与 F1 扫描

## 4. 功能逻辑（按跳转解释）

### 4.1 为什么做成「查询级」而不是「片段级」

**触发点**：设计校准方案时

```
片段级标注有天然歧义：
   「不在 expected_chunk_ids 里」≠ 不相关
   （一个问题的答案常同时出现在多个片段）
   → 把非 gold 片段标成「不相关」会系统性污染阈值

真实决策是查询级的：
   「这个工单到底有没有可用资料？」
   → 正样本 164 条 = 有资料（label 1）
   → 负样本 36 条  = 无资料（label 0）
   → 特征 = 该次检索的**最高分**
```

**技术栈：** 无（建模方法）

### 4.2 特征选择：三个候选，只有一个能用

**触发点**：`python -m evaluation.calibrate_threshold`

```
=== 特征 max_dense（稠密余弦）===
  正样本: min=0.424 p50=0.728 max=0.932 均值=0.719
  负样本: min=0.264 p50=0.377 max=0.480 均值=0.368
  → 阈值 0.513: precision=1.000 recall=0.994 F1=0.997（5折CV F1=0.993）

=== 特征 max_sparse（BM25 原始分）===
  正样本: min=6.238  p50=16.914 max=42.521 均值=18.813
  负样本: min=3.016  p50=8.498  max=16.480  均值=8.406
  → **分布严重重叠**：正样本最低 6.2 低于负样本最高 16.5
  → 最佳 F1 仅 0.932，误收 17 条

=== 特征 top1_rrf ===
  正样本 0.030~0.033，负样本 0.030~0.033
  → 几乎无区分度（F1=0.905，漏判 17）
```

**结论**：

- ✅ **稠密余弦分**：有界 [0,1] 且**跨查询可比**，正负分布分离良好 → 用它。
- ❌ **BM25 原始分**：受查询长度与词频影响，**不可跨查询比较** → 不能用。
- ❌ **RRF**：本质是排名融合系数，**无相关性含义** → 不能用。

**技术栈：** Milvus COSINE 相似度 · BM25 分数 · 分位数统计

### 4.3 阈值选择：不取 F1 最优点

**触发点**：拿到 F1 最优阈值 0.513 后核对漏判代价

```
F1 最优 = 0.513，但漏判 2 条。
关键问题：这 2 条的 gold 是不是本来就被召回了？
   S062 max_dense=0.424  gold 被召回=True  ← 本来能答对！
   S063 max_dense=0.513  gold 被召回=True  ← 本来能答对！
→ 那是**真实损失**，不是「反正也答不对」的白白拦截
```

**两种误判代价不对称**：

| 误判 | 含义 | 代价 |
| --- | --- | --- |
| 漏判（false reject） | 本可答对的问题被拒答 | **高**：用户得不到答案 |
| 误收（false accept） | 无关问题仍拿到片段 | 低：生成层还有一道拒答闸 |

完整权衡曲线（`_verify_threshold.py` 实测）：

| 阈值 | 漏判 | 误收/36 | 拦截率 |
| --- | --- | --- | --- |
| 0.40 | 0 | 14 | 61% |
| **0.42** | **0** | **7** | **81%** |
| 0.45 | 1 | 2 | 94% |
| 0.50 | 1 | 0 | 100% |
| 0.513（F1最优） | **2** | 0 | 100% |

→ **取 0.42**：不误杀任何可回答的问题，同时拦掉 81% 的无关检索。
**F1 最优值反而不是好选择**——这正是「先看代价、再看指标」的意义。

**技术栈：** 混淆矩阵扫描 · 与检索评估报告按 id 关联核对 gold 是否被召回

### 4.4 门槛落地与降级保护（修掉一个自己引入的 bug）

**触发点**：`hybrid_search()` 第 6 步

```
final = candidates[:top_k]
   ↓
max_dense = max(各片段 dense_score)
rejected = bool(final) and not passes_relevance_gate(final, relevance_min_dense)
   ↓ rejected=True → final = [] → 上层走 NOT_FOUND_REPLY / 转人工
```

**实现时踩到的真实 bug（已被 9 个失败测试抓出）**：

```
初版：any((c.dense_score or 0.0) >= min_dense for c in chunks)
   → 稠密通道降级为纯 BM25（SPARSE_ONLY）时，所有片段 dense_score=None
   → 门槛把**每个问题**都判成「无可用资料」
   → 整条链路在降级模式下直接瘫痪
```

修法：**没有任何稠密分时无法判定，必须放行**——
降级模式下宁可误收，也不能让系统全面拒答（与 4.3 的代价原则一致）。

```python
scores = [c.dense_score for c in chunks if c.dense_score is not None]
if not scores:
    return True  # 无法判定 → 放行，交由生成层拒答
```

**技术栈：** 纯函数 + 显式降级分支

### 4.5 评估链路对齐

**触发点**：`run_system()`

```
chunks 为空（无命中 或 被门槛拦截）
   → 此前：answer = ""（虽被 is_refusal 判为拒答，但与线上不一致）
   → 现在：answer = NOT_FOUND_REPLY（与线上链路一致，且不调用生成）
```

已验证 `is_refusal(NOT_FOUND_REPLY) is True`，指标口径不会失真。

**技术栈：** `app/generation/prompts.NOT_FOUND_REPLY`

## 5. 关键实现说明

| 项 | 说明 |
| --- | --- |
| **只判稠密分** | BM25 原始分不可跨查询比较（实测正负分布重叠），RRF 是排名分 |
| **无稠密分必须放行** | 否则纯 BM25 降级模式下会全量拒答（真实 bug，已修） |
| **区分「无命中」与「被拦截」** | `final` 为空不算拦截；`debug["relevance_rejected"]` 单独标记，便于归因 |
| **阈值不取 F1 最优** | 代价不对称：漏判 >> 误收。0.42 优于 0.513 |
| **`debug["max_dense"]` 落盘** | 让每次检索都能看到实际分数，便于后续重新校准 |
| **门槛可关闭** | `RELEVANCE_MIN_DENSE=0` 即关闭，便于 A/B 对比 |

## 6. 验证方式

```bash
pytest -q                                    # 168 passed
python -m evaluation.calibrate_threshold     # 校准 + 5 折 CV
python -m evaluation.run_retrieval_eval      # 验证门槛实际效果
```

**单元测试（新增 8 个）：** 门槛关闭、任一达标即通过、全部低于则拦截、边界值、
**全部缺分必须放行（纯 BM25 降级）**、部分缺分以有分为准、空结果放行。

**端到端效果（门槛 0.42 启用前后对照）：**

| 指标 | 启用前 | 启用后 |
| --- | --- | --- |
| 正样本 Hit Rate@8 | 99.39% | **99.39%（无变化）** |
| 正样本 Recall@8 | 97.97% | 98.27% |
| 正样本 MRR | 0.8412 | 0.8443 |
| **负样本返回非空比例** | **100%** | **19.44%** |
| 未命中样本 | 1 条 | 1 条（同一条 S028） |

→ 正样本零损失，负样本拦截 81%（29/36）。

## 7. 局限与待办

- [ ] **⚠️ 81% 拦截率是乐观值**：负样本全部是**领域遥远**的问题
      （年假、绿植、团建、工位桌牌）。真实的「领域接近但超范围」问题
      （如「VPN 支持 Linux 吗？」而知识库只写了 Windows/macOS）稠密分会高得多，
      **门槛大概率拦不住**。要得到真实拦截率，需要一批真实工单中的超范围问题。
- [ ] **阈值贴着正样本最小值**：0.42 仅比观测到的正样本最低分 0.424 低一点点，
      样本量增大后正样本最小值可能更低 → 需定期用 `calibrate_threshold.py` 重校。
- [ ] **只用了单特征**：未尝试「稠密 + 稀疏分位数归一化」的组合特征，
      理论上能救回 S062（dense 0.424 但 gold 已召回）这类样本。
- [ ] **未做分域校准**：不同来源（manual/faq/ticket）的分数分布可能不同，
      当前是全局单一阈值。
- [ ] **生成层效果未复测**：门槛启用后负样本不再调用生成，
      `run_generation_eval` 的拒答率与延迟应重新跑一次确认（本次未跑）。
- [ ] **未验证线上并发下的稳定性**：embedding 抖动会影响 dense 分，进而影响拦截判定。
