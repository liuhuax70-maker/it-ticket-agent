## 1. 在整体布局中的位置（从底层到总体）

从底层到总体，项目共 6 层。**本次加入的是最底下的两层地基**：

```
第 6 层  部署           deploy/  Dockerfile · docker-compose.yml        ← 本次（空壳）
第 5 层  接入           app/api/  health · ticket · session · retrieval  ← 本次（仅 health 可用）
第 4 层  编排           app/graph/  state · build · nodes/*             ← 本次（仅 state 实体）
第 3 层  能力           app/retrieval/ · app/generation/ · app/memory/  ← 本次（仅 fuse 实现）
第 2 层  契约与配置      app/schemas/ · app/core/                        ← 本次（完整）
第 1 层  运行时          app/main.py · requirements.txt · .env.example   ← 本次（完整）
```

**依赖方向**：上层依赖下层，下层不感知上层。

- `app/core/config.py` 被**所有模块**依赖（最底层，无依赖）。
- `app/schemas/` 被 `api` / `graph` / `retrieval` 共同依赖（数据契约）。
- `app/retrieval/fuse.py` 只依赖 `schemas`，因此可以独立测试——本次用它来**验证骨架是通的**。

**为什么先立骨架**：后续每加一个框架/功能，都只是往既有「抽屉」里放东西，目录与依赖方向不再变动，避免后期大范围重构。

**技术栈：** Python 3.11 · FastAPI 0.139 · Pydantic v2 · pydantic-settings · Docker Compose

## 4. 功能逻辑（按跳转解释）

### 4.1 应用启动与请求进入

**触发点**：进程启动 → `uvicorn app.main:app` → 模块级执行 `app = create_app()`。

```
import app.main
   └─► create_app()
         ├─► get_settings()                 # 读 .env → Settings 单例
         ├─► FastAPI(lifespan=...)          # lifespan 内做 setup_logging
         ├─► @app.middleware("http")        # 注册 trace_id 中间件
         ├─► register_exception_handlers()  # 注册 3 个异常处理器
         └─► app.include_router(api_router, prefix="/api/v1")
   └─► @app.get("/")                        # 根路径元信息

请求到达：
HTTP 请求 → trace_id 中间件 → 路由匹配 → 端点函数
                                   │
                          抛错? ───┼── AppError ──────────► AppError 处理器（业务错误码）
                                   ├── 参数校验失败 ───────► ValidationError 处理器（1001）
                                   └── 其他异常 ───────────► 兜底处理器（9000）
```

**技术栈：** Python · FastAPI（ASGI）· uvicorn · lifespan 上下文管理器

### 4.2 trace_id 中间件

**触发点**：任意 HTTP 请求进入。

- 若请求头带 `X-Trace-Id` 则复用，否则 `uuid4().hex[:16]` 生成；
- 写入 `request.state.trace_id`（供异常处理器与端点读取）；
- 回写到响应头 `X-Trace-Id`，实现「一个请求，一条链路」可追踪。

**技术栈：** Starlette `BaseHTTPMiddleware`（`@app.middleware("http")`）· uuid4

### 4.3 统一异常与错误码

**触发点**：任何端点抛出异常时。

- 业务代码抛 `AppError(code, message, detail)`；
- 处理器按 `_HTTP_STATUS` 映射表转换 HTTP 状态码，输出统一响应体；
- 参数校验由框架抛 `RequestValidationError` → 固定为 `1001`；
- 其余未捕获异常记录堆栈后统一返回 `9000`，避免泄露内部信息。

**技术栈：** Python `enum.IntEnum` · FastAPI `exception_handler` · JSONResponse

### 4.4 健康检查（依赖探测）

**触发点**：`GET /api/v1/health`。

```
读 settings → 解析 Milvus(host,port) 与 Ollama(url→host,port)
   └─► asyncio.gather(两个 TCP 探测, 超时 1s)
         ├─ 全部 up   → status = healthy
         ├─ 部分 up   → status = degraded
         └─ 全部 down → status = unhealthy
   └─► 组装 dependencies 明细返回
```

- 设计要点：**不因依赖不可用而返回 5xx**，而是用 `status` 表达，供容器探活与运维判断；
- 当前实测（本地未启动 Milvus/Ollama）：`degraded`，`milvus=down, ollama=down`。

**技术栈：** asyncio（`open_connection`）· urllib.parse · Starlette Request

### 4.5 数据契约（Pydantic v2）

**触发点**：所有接口的入参与出参。

- 请求模型（`TicketQueryRequest` / `ReviewRequest` / `SearchRequest`）由 FastAPI 自动校验并生成 OpenAPI；
- 枚举（`Intent` / `Source` / `ReviewStatus` / `SendStatus` / `TicketStatus` / `DocSource` / `RetrievalMode`）与 `开发流程/05` §2.1 一一对应，**编排 State 与 API 共用同一套枚举**，避免各处各定义；
- `ApiResponse[T]` 用 `Generic` + `TypeVar` 实现泛型响应。

**技术栈：** Pydantic v2 · `typing.Generic` / `TypeVar` · FastAPI OpenAPI 自动生成

### 4.6 RRF 融合（本次唯一完整实现的算法）

**触发点**：混合检索拿到两路有序结果后调用。

```
dense 结果（按分降序）┐
                      ├─► reciprocal_rank_fusion()
sparse 结果（按分降序）┘        │
                                 ├─ 对每路按位置取 rank（从 1 开始）
                                 ├─ score[d] += 1/(k + rank)，k=60
                                 ├─ 按 score 降序排序
                                 └─ 回写 rrf_score 与 rank，可按 top_n 截断
```

- 关键决策：**按排名而非分数融合**，因为稠密（余弦相似度）与 BM25（无上界分数）量纲不一致，直接相加/加权都需要调参；
- `chunk_id` 作为跨通道对齐键（同一片段在两路中各有一个排名）。

**技术栈：** Python `collections.defaultdict` · Pydantic `model_copy(update=...)`

### 4.7 配置注入

**触发点**：任何模块调用 `get_settings()`。

```
环境变量 / .env  ──►  pydantic-settings  ──►  Settings 实例（@lru_cache 单例）
                                              └─► 全项目共享，字段名大小写不敏感
```

**技术栈：** pydantic-settings（`BaseSettings` + `SettingsConfigDict`）· `functools.lru_cache`

## 5. 关键实现说明

| 项 | 说明 |
| --- | --- |
| 配置来源 | `.env`（`env_file=".env"`，`extra="ignore"` 容忍无关变量） |
| 默认值取向 | `MILVUS_HOST` / `OLLAMA_BASE_URL` 默认 `localhost`，便于本地直跑；`.env.example` 用容器服务名 `milvus` / `ollama` |
| 端口探测超时 | `_PROBE_TIMEOUT = 1.0s`，避免健康检查被慢依赖拖死 |
| 幂等 | `Settings` 使用 `@lru_cache`，进程内只读一次环境变量 |
| SSE 依赖 | **未引入 `sse-starlette`**，后续用 Starlette 原生 `StreamingResponse` 即可，少一个依赖 |
| Compose 路径 | `deploy/docker-compose.yml` 的 `build.context: ..`，Dockerfile 相对根目录 COPY |
| 容器内路径 | compose 用 `environment` 覆盖 `CHECKPOINTER_PATH=/data/checkpoints.sqlite`，挂载 `checkpoint_data` 卷 |

## 7. 验证方式

在项目根目录执行（本机 Python 3.11.9）：

```bash
# 1) 导入与路由挂载
python -c "from fastapi.testclient import TestClient; from app.main import app; print(TestClient(app).get('/api/v1/health').json())"

# 2) 单元测试（需先 pip install -r requirements.txt）
pytest -q
```

| 检查 | 结果 |
