## 1. 在整体布局中的位置（从底层到总体）

本次加入的是**知识库入库流水线的第一道工序**，位于检索能力的最上游：

```
第 6 层  部署
第 5 层  接入
第 4 层  编排
第 3 层  检索/知识        ingestion/chunk.py  ← 本次（切分 + 元数据抽取）
                              │
                              ▼
                        ingestion/ingest.py   （下一步：向量化 + 写入 Milvus）
                              │
                              ▼
                        app/retrieval/*       （再下一步：稠密/稀疏检索）

第 1 层  运行时
```

- **依赖谁**：只依赖 Python 标准库（`re` / `hashlib` / `dataclasses`）——**零外部依赖**，因此可以独立、快速地单元测试。
- **被谁依赖**：`ingestion/ingest.py` 将消费 `split_document()` 的产出写入 Milvus。
- **为什么要有它**：RAG 的检索质量首先取决于「切得对不对」。切分粒度不当、元数据丢失，后面的 RRF 与重排都救不回来。

**技术栈：** Python 3.11 标准库（`re` · `hashlib` · `dataclasses`）· pytest 9.1.1

## 4. 功能逻辑（按跳转解释）

### 4.1 切分总流程

**触发点**：`split_document(doc_id, text, chunk_size, overlap, title)`

```
text
 │
 ├─ 空文本? ──是──► 返回 []
 │
 ├─ overlap >= chunk_size? ──是──► 抛 ValueError（参数不合法，快速失败）
 │
 ▼
① _split_blocks()      按标题/空行 → [(所属标题, 文本块), ...]
 │                        └─ 纯标题块（无正文）不落块，与后续正文合并
 ▼
② _split_long_text()   每个块若超预算 → 按句子切成多个 unit（单句超长再按字符硬切）
 │
 ▼
③ 累加循环             逐个 unit 累加，遇到「标题变化」或「超预算」就开启新块
 │                        └─ 开启新块前先用 _tail_by_tokens() 取上一块尾部作为重叠
 ▼
④ flush()              content → extract_metadata() → RawChunk(doc_id, index, ...)
 │
 ▼
list[RawChunk]  →（可选）dedupe_chunks()
```

**技术栈：** Python · `re`（`HEADING_RE` 结构识别、`_SEG_SPLIT` 分段、`_SENT_SPLIT` 断句）· `dataclasses`

### 4.2 标题 / 段落分块（结构感知）

**触发点**：扫描到 Markdown 标题行或空行。

```
逐行读取
  ├─ 匹配 HEADING_RE (# ~ ######)? ──是──► 先 flush 缓冲，记录 current_heading，标题行入缓冲
  ├─ 该行为空行? ──────────────────是──► flush 缓冲
  └─ 普通正文行 ────────────────────────► 入缓冲

flush 规则：
  content 为空                → 什么都不做
  content 只有标题行（无正文） → 不落块，继续留在缓冲（并入后续正文）
  否则                        → blocks.append((current_heading, content))
```

- 关键设计：**标题行本身保留在块内容里**，这样检索时标题词（如「常见错误码」）也能被命中。
- 纯标题块不与正文合并的话，会产生「只有一行标题」的低价值 chunk（实测把 8 块降到 5 块就是因为这个修正）。

**技术栈：** Python `re`（`^\s{0,3}#{1,6}\s+(.*\S)\s*$`）

### 4.3 超长块二次切分

**触发点**：某个块 `estimate_tokens(block) > chunk_size`。

```
块文本
  └─ 按 _SENT_SPLIT（。！？!?；; \n 之后）切成句子
        ├─ 单句 token > 预算 ──► _hard_split() 按字符硬切（step = chunk_size）
        └─ 否则累加句子，累计超预算就切一片
```

- 保证「每个 unit 都不超过 chunk_size」，这是后续累加逻辑正确的前提。

**技术栈：** Python `re` 零宽断言（`(?<=[...])`）保留标点

### 4.4 累加与重叠窗口

**触发点**：遍历 unit 时判断是否开启新块。

```
对每个 unit:
   if 缓冲非空:
       标题变化（heading != buf_heading，且 heading 非空）──► 开启新块
       或 缓冲 token + unit token > chunk_size ───────────► 开启新块

   开启新块时:
       tail = _tail_by_tokens(缓冲文本, overlap)     # 上一块尾部
       flush()                                        # 落块并清空缓冲
       若 tail 非空 ──► 缓冲 = [tail]，新块以 tail 开头（重叠上下文）
       buf_heading = 当前 unit 的标题

   缓冲 = 缓冲 + [unit文本]
```

- 重叠取法优先「整段回退」；若单段就超过重叠预算，退化为**按字符近似回退**并尽量对齐句读。
- 单块上限为 **`chunk_size + overlap`**（软约束）：如果严格要求 ≤ chunk_size，重叠在「unit 接近满额」时会永远失效，反而失去上下文。

**技术栈：** Python（列表缓冲 + nonlocal 闭包）

### 4.5 元数据抽取

**触发点**：每次 `flush()` 落块时。

```
块内容
  ├─ VERSION_RE      \bv?\d+(?:\.\d+){1,3}\b      → v1.2.3 / 1.2
  └─ ERROR_CODE_RE   \b(?:ERR|E)[-_]?\d{3,5}\b    → ERR-4041 / E4041（忽略大小写）
        └─► RawChunk.version / RawChunk.error_code
```

- 抽的是**块级**元数据（不是文档级），因为同一文档不同段落可能涉及不同版本/错误码。
- 这些字段后续会作为 Milvus **标量字段**参与过滤（如按 `error_code` 精确过滤）。

**技术栈：** Python `re` · dataclass 字段

### 4.6 去重

**触发点**：入库前调用 `dedupe_chunks(chunks)`。

```
对每个 chunk:
   hash = sha256(去掉所有空白后的 content)
   hash 已见过? ──是──► 跳过
                 └─否──► 保留，记入 seen
```

- 去掉空白再哈希，因此「空格/换行差异」的重复内容也能识别（有对应用例）。
- 目的：避免重复片段在检索结果里「刷榜」，挤占 Top-K。

**技术栈：** `hashlib.sha256` · `set`

## 5. 关键实现说明

| 项 | 说明 |
| --- | --- |
| **token 估算公式** | `CJK 字数 × 1 + 英文/数字词数 × 1 + 标点数 × 0.5`（取整）。不引入 tokenizer，保证零依赖、跨环境一致 |
| 参数校验 | `overlap >= chunk_size` 或 `overlap < 0` 直接抛 `ValueError`，避免静默产出错误切分 |
| 标题变化即分块 | 保证「一节一块」的结构语义，也让 `title` 字段有意义 |
| `chunk_id` | `f"{doc_id}#{chunk_index}"`，稳定可复现，便于引用与去重 |
| 正则的边界 | 版本号用 `\b` 包裹避免匹配到 `4041` 这类纯数字；错误码要求 `ERR/E` 前缀，避免把普通数字当错误码 |
