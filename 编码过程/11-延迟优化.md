## 1. 在整体布局中的位置（从底层到总体）

本节点不新增能力，而是**给已有链路装上「秒表」并拿掉最贵的开销**——横跨生成层与评估层。

```
第 5 层  接入            app/api/*（SSE 已在推 token，用户感知的是 TTFT）
第 4 层  编排            app/graph/*
第 3 层  能力
   ├── app/generation/ollama.py   ← 本次改造：计量 + num_predict + keep_alive
   └── app/retrieval/*            被测量对象（未改动）
第 2 层  契约与配置        app/core/config.py  ← 新增 llm_num_predict / llm_keep_alive
──────────── 横向 ────────────
      evaluation/
        ├── run_latency_profile.py  ← 新增：分阶段剖析 + 模型对比
        └── run_generation_eval.py  ← 增强：记录并报告 P50/P95 延迟
```

- **依赖谁**：既有检索与生成链路 + 本地 Ollama。
- **被谁依赖**：评估报告（延迟进入验收指标）、后续模型选型决策。
- **为什么要有它**：要点文档 §3.7 明确「一次问答 = embedding + 向量检索 + BM25 + rerank + LLM 生成，串行叠加很容易 3~5 秒起步」，
  且要求「P95 延迟」必须能随时报出。**没有分段计时，优化只能靠猜。**

**技术栈：** `time.perf_counter` 分段计时 · Ollama `/api/chat` 返回的 `*_duration` 计量字段 · 流式首 token 计时（TTFT）

## 4. 功能逻辑（按跳转解释）

### 4.1 延迟剖析方法

**触发点**：`python -m evaluation.run_latency_profile`

```
① 检索阶段（profile_retrieval）
   先 embed(["预热"])               ← 关键：不预热则首条 query 的冷 embed 会污染后续差值
   对每条 query 分别计时：
      embed([q])                → embedding 耗时
      search_dense(q, N)        → 含内部 embed 的稠密链路
      search_sparse(q, N)       → BM25 耗时
      hybrid_search(q, top_k)   → 混合检索整体（并行两路 + 融合 + 去重）

② 生成阶段（profile_generation）
   先做一次极短预热（回复「好」）     ← 记录**冷加载**耗时
   对每条 query：
      hybrid_search → build_context → generate_detailed(...)
        ├─ TTFT（首个非空增量到达时刻）
        ├─ total_seconds
        └─ Ollama 计量：load/eval/prompt_eval duration、eval_count

③ 汇总 P50 / P95 / min / max，写入 evaluation/reports/latency_*.json
```

**技术栈：** `time.perf_counter` · Ollama `total_duration` / `load_duration` / `eval_count` / `eval_duration`

### 4.2 检索阶段结论

**触发点**：`--skip-generation`

```
=== 检索阶段（毫秒，6 条 query）===
  query                          embed    稠密    稀疏    混合
  ERR-4041 是什么错误…            842.9   121.7    4.9   789.5
  ERR-5002 报错是什么原因？          916.7  -128.9    4.4   834.0
  升级到 v1.3.0 之后…             852.7     9.2    5.2   800.7
  登录模块手册适用于哪些版本？           793.5     2.8    4.1   871.2

  embedding      mean= 853.9ms  p95= 916.7ms
  稠密检索(Milvus) mean= -11.8ms  p95= 121.7ms   ← 见下说明
  稀疏检索(BM25)  mean=   4.5ms  p95=   5.2ms
  混合检索整体     mean= 828.0ms  p95= 873.7ms
```

- **结论 1：检索侧延迟 ≈ embedding 调用（~850ms），占混合检索整体的 100%。**
  Milvus 的 ANN 与 BM25 合计不到 10ms —— 向量库不是瓶颈。
- **结论 2**：稠密列的负值说明「Milvus ANN 开销小于 embedding 调用的抖动（±100ms）」，
  即 **ANN 耗时可忽略**，不是测量错误（这是把 850ms 的噪声减出来的必然结果）。
- **优化方向**：要压检索延迟，只有两条路 —— 缓存 query embedding，或换更小的 embedding 模型；
  调 Milvus 索引参数没有意义。

**技术栈：** Python 分段计时 · 差值法隔离子阶段

### 4.3 生成阶段结论

**触发点**：`--models qwen3.5:9b,qwen3.5:4b`

```
=== 生成阶段（2 条 query）===
  model          num_predict   TTFT(s)  总耗时(s)  输出tok   tok/s
  qwen3.5:9b               0      4.0      11.8     176    14.9
  qwen3.5:4b               0      3.3       5.6      64    11.2

  冷加载观测（预热调用的 load_duration）：
    qwen3.5:9b   load=12.0s
    qwen3.5:4b   load=13.4s

  延迟构成（均值）：
    qwen3.5:9b   首token=4.0s（prefill） + 后续生成=7.8s = 11.8s
    qwen3.5:4b   首token=3.3s（prefill） + 后续生成=2.3s =  5.6s
```

三条重要结论：

1. **生成速率差距很小，输出长度差距很大。**
   9b 与 4b 的原始速率分别为 **22.6 / 27.7 tok/s**（仅差 23%），
   但 4b 在同一 prompt 下只输出 **64** token，9b 输出 **176** token —— 总耗时差 2 倍主要来自**回答长度**。
   → **真正的主导变量是输出 token 数**（`总耗时 ≈ prefill + 输出token数 ÷ 速率`）。
2. **冷加载 12~13s，与模型大小几乎无关**（磁盘 IO 为主）。
   若不加保活，每次冷启动都会白付 12s。已通过 `LLM_KEEP_ALIVE=30m` 解决。
3. **TTFT 3.3~4.0s**：对一条约 960 token 的 prompt 来说偏慢（prefill 慢），
   占 9b 总耗时的 34%。SSE 已经在推 token，用户实际感知的等待就是这段 TTFT。

**技术栈：** Ollama 计量字段 · 流式首 token 计时

### 4.4 参数控制落地

**触发点**：`app/generation/ollama.py::_payload()`

```
num_predict：
   settings.llm_num_predict（默认 0=不限）
      └─ >0 才写入 options.num_predict   ← 0/None 不写，避免被模型当成「输出 0 token」

keep_alive：
   settings.llm_keep_alive（默认 "30m"）
      └─ 非空才写入 payload.keep_alive
```

**技术栈：** Ollama `/api/chat` 的 `options.num_predict` 与顶层 `keep_alive`

### 4.5 评估链路接入延迟

**触发点**：`run_system()` 与 `run_generation_eval`

```
run_system(item)
   ├─ t0 ─► hybrid_search ─► retrieval_seconds
   ├─ t1 ─► build_context + generate ─► generation_seconds
   └─ EvalRun(retrieval_seconds, generation_seconds, total_seconds)

run_generation_eval
   └─ _latency_summary(rows) ─► {检索/生成/合计} × {P50, P95, max}
```

- 从此**质量与延迟在同一份报告里**，避免「优化了延迟却偷偷降低质量」这类无感退化。

**技术栈：** dataclass 属性 · 分位数统计

## 5. 关键实现说明

| 项 | 说明 |
| --- | --- |
| **必须先预热再测量** | 首条 query 的冷 `embed`（4.2s）会让「稠密检索 = 稠密总耗时 − embed」算成负数；预热后差值才有意义 |
| **计量日志是顺手做的成本观测** | 要点文档 §3.7 要求「分别埋 embedding token、LLM input/output token」，`_log_metrics` 已覆盖 LLM 侧 |
| **`num_predict=0` 不写进 options** | 写成 0 会被模型理解为「不输出」，必须**省略**该字段 |
| **tok/s 要剔除加载耗时** | 否则冷启动那一次会把速率算得极低（本次实测 42.2 → 22.6 tok/s），污染对比 |
| **延迟必须在无并发负载时采集** | 见 §6 —— 这是本次最重要的方法论教训 |
| **不盲目改默认模型** | 4b 更快但回答更短，**质量是否下降尚未验证**，因此保持 9b 为默认，只提供切换方式 |

## 6. 一个必须记下的方法论教训 ⚠️

同一套代码、同一个问题，两次测得的生成耗时差了 **7 倍**：

| 测量时间 | 单条正样本生成耗时 | 备注 |
| --- | --- | --- |
| 评估节点首次运行 | **~85s** | 当时用户把 RAGAS / 生成评估**切到后台运行** |
| 本次剖析 | **11.8s** | 无其他负载 |

**结论：延迟数据必须在无并发负载时采集。** 后台还跑着另一个打 Ollama 的任务时，
两个任务争抢 CPU/GPU，得到的数字比真实值差一个数量级，据此做优化决策会完全跑偏。

> 这条同样适用于质量评估：并发的 LLM 裁判任务会拖慢被测系统，进而影响超时类降级分支的触发概率。

## 8. 优化结论与建议

| 措施 | 收益 | 是否已落地 |
| --- | --- | --- |
| `keep_alive=30m` 保活 | 省掉每次 **12~13s** 冷加载 | ✅ 已落地 |
| 生成计量与日志 | 可观测、可按 token 计成本 | ✅ 已落地 |
| 评估记录 P50/P95 | 延迟进入验收口径 | ✅ 已落地 |
| **限制输出长度**（`num_predict`） | **最直接**：输出减半即耗时减半 | ⚙️ 已支持，默认不限（避免截断回答），需按场景设定 |
| 换 `qwen3.5:4b` | 实测 11.8s → 5.6s | ⚙️ 已支持 `LLM_MODEL` 切换，**待质量对比后决定** |
| query embedding 缓存 | 检索侧省掉 ~850ms 中的大部分 | ⏳ 未做 |
| GPU 加速 | 直接提升生成速率与 prefill | ⏳ 依赖硬件 |

**给生产的三条建议**（按 ROI）：

1. **先给 `num_predict` 设一个业务可接受的上限**（如 512）——
   本地场景下这是唯一「改一行、立省一半」的开关。
2. **压 TTFT**：TTFT 3~4s 对 SSE 体验影响最大，最有效的办法是**缩短 prompt**（降 `top_k` 或收紧 `context_max_chars`）。
   注意这与 Recall 是权衡，`top_k` 已由扫参定为 8。
3. **模型选型要带质量一起测**：4b 快一倍但回答短了 2/3，
   必须用 `run_generation_eval` 对比「拒答率 + 引用回链正确率」后再决定，不能只看速度。

## 9. 待办 / 注意

- [ ] **4b vs 9b 质量对比未完成**：需要在无负载条件下各跑一次 `run_generation_eval`（含负样本拒答率）。
- [ ] **`num_predict` 默认仍为 0**：建议按业务上限收紧，但要先确认不会截断关键步骤。
- [ ] **query embedding 无缓存**：同一问题重复提问仍要付 ~850ms。
- [ ] **TTFT 未进入正式验收阈值**：`06-测试与验收方案` 的 P95 阈值尚未按实测更新。
- [ ] **未测并发**：本节点只测了单请求延迟，多请求并发下的排队行为未评估。
- [ ] **未验证 GPU 场景**：当前数据来自本地 CPU/集成显卡环境，不能外推到 GPU 部署。
- [ ] 后台任务与测量任务**不能同时跑**（见 §6），后续评估建议串行执行。
