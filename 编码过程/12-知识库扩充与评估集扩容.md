## 4. 功能逻辑（按跳转解释）

### 4.1 为什么「扩到 200 条」必须先扩知识库

**触发点**：准备扩容评估集时发现

```
知识库只有 15 个片段（3 篇文档）
   → 200 条问题 ÷ 15 片段 = 每个片段 13 条
   → 且 Recall@8 在 15 片段库中随机命中率 = 8/15 ≈ 53%
   → 指标虚高且对优化不敏感
```

**不做这一步，200 条只是把噪音放大 8 倍。** 所以先扩内容，再扩评估集。

**技术栈：** 无（分析方法）

### 4.2 知识库扩充

**触发点**：`knowledge_base/` 新增文档 → `python -m ingestion.ingest --recreate`

```
新增文档（均为 IT 运维常见域，与登录域形成干扰项）
   manual/vpn-access.md           ERR-7001/7002/7003 · v2.1.0~v2.4.3
   manual/mail-client.md          ERR-3102/3105/3108 · v3.4.2
   manual/endpoint-protection.md  ERR-8801/8804/8809 · v5.0.1~v5.2.0
   faq/network-issues.md          无线/DNS/内网慢/访客网络
   faq/account-permission.md      权限申请/密码策略/离职交接/MFA
   tickets/history.jsonl          T-1006 ~ T-1011（覆盖新域）

   ↓ 切分 + qwen3-embedding 向量化 + upsert

Milvus: 15 → 46 片段（manual 20 / faq 15 / ticket 11）
```

**刻意保留跨域相似性**（如 ERR-4041 登录 vs ERR-7001 VPN），
让检索存在真实干扰项，否则 Recall 仍会虚高。

**技术栈：** Markdown/JSONL 源文档 · `ingestion/chunk.py` · `qwen3-embedding:0.6b` · Milvus upsert

### 4.3 评估集生成器：生成 + 校验

**触发点**：`python -m evaluation.generate_testset`

```
① 从 Milvus 读取全部 46 个片段
② 逐片段出题（每片段 3~4 条，风格三轮换）：
     偏专有名词/错误码  →  BM25 强项类问题
     偏口语化          →  稠密向量强项类问题
     偏场景化          →  真实用户表述
③ 要求模型同时给出「答案要点」，且必须是片段原话
④ 校验：归一化(答案) ⊆ 归一化(片段) ？  ← 核心闸
      不通过 → 丢弃并记录
⑤ 同片段内按答案要点去重（换皮问题只留一条）
⑥ 追加写入 testset.jsonl，跳过已达标的片段（支持续跑）
```

**技术栈：** Qwen3.5:9b · Milvus `query()` · 归一化字符串包含校验

### 4.4 四道质量闸（这是本次的核心价值）

| 闸 | 为什么必须有 | 不做的后果 |
| --- | --- | --- |
| **答案必须是片段原话** | 否则模型可能问到片段外的内容，「系统没召回」会被误判成「检索差」 | `expected_chunk_ids` 标注失真，指标彻底不可信 |
| **同片段内答案去重** | 实测第一版同一片段生成的 4 条问题**全部等价**（S001~S004 都是「升级后被踢下线」的换皮） | 200 条实际只有几十条的信息量，Recall 被同一结果重复计数 |
| **负样本领域隔离** | 负样本必须真的答不了 | 把可回答问题标成负样本，拒答率指标失真 |
| **编造错误码拦截** ⭐ | 见下方 4.4.1 | 坏样本被误记为检索缺陷 |

> **第一版的教训**：不加强制去重时，模型对一个片段稳定产出 4 条同义问题，
> 且答案要点几乎都是整段照抄。修正后重复率从「近乎 100%」降到 **14.6%**。

**技术栈：** 归一化后字符串比较 · 领域关键词正则（`ERR-[A-Za-z0-9-]+` / `v\d+\.\d+` / 领域词表）

#### 4.4.1 编造错误码：一道差点漏掉的闸

**触发点**：首批 200 条跑完检索评估，3 条未命中里有 2 条看着不对劲

```
S035 「提示 ERR-EXPIRE-NOTICE 时，系统会在到期前多少天开始提醒？」
S081 「ERR-VERSION-MISMATCH 错误通常出现在什么版本以下？」
   → 知识库里根本没有这两个错误码，是模型编造的
   → 但「答案要点必须是原话」这道闸放行：答案确实是原话
   → 系统自然检索不到 → 被记成「检索失败」
   → 实际是**评估集自身的标注错误**
```

加闸后全量审计：**144 条合成样本里有 11 条（7.6%）含编造错误码**
（`ERR-PWD-LEN`、`ERR-MFA-REBIND`、`ERR-VPN-DIVERT`、`ERR-MAIL-001` …）。

**为什么只拦错误码、不拦版本号**：错误码是离散标识，编造即错；
版本号是连续区间，问「v5.1 能用吗」而原文写「v5.0.1 至 v5.2.0」是合理简写。
实测确实出现这类误判（`S067`），一并拦截会误杀正常样本。

**效果验证**（最有说服力的一点）：

| | 清洗前 | 清洗后 |
| --- | --- | --- |
| 未命中样本 | 3 条 | **1 条** |
| Hit Rate@8 | 98.17% | **99.39%** |

→ 证明那 2 条确实是坏样本而非检索缺陷。**如果不修，会一直把它们当成待优化的缺陷。**

**技术栈：** `ERR-[A-Za-z0-9-]+` 正则 + 归一化包含校验

### 4.5 分批改跑（续跑机制）

**触发点**：46 个片段 × ~12s/次 ≈ 9 分钟，单次执行易被中断

```
counts = 各片段已生成条数（从已有 testset.jsonl 反推）
   ↓
跳过 counts[chunk] >= per_chunk 的片段
   ↓
--chunk-offset / --chunk-limit 分批
--style-offset 1 第二轮换风格，避免与第一轮问法重复
```

**技术栈：** 追加式写入 + 幂等跳过

### 4.6 手工 vs 合成分开统计

**触发点**：`EvalItem.source`

```
manual    （26 条）人工编写，可信度最高
synthetic （174 条）模型生成并通过原话校验

→ 报告时可只统计 manual 子集，避免「合成样本刷量」掩盖真实质量
```

**技术栈：** dataclass 字段 + `type` 三值（lexical / semantic / negative）

## 5. 关键实现说明

| 项 | 说明 |
| --- | --- |
| **`type` 判定只看错误码** | 第一版把含 `v1.3.0` 的问题也算 lexical，但「升级 v1.3.0 后被强制退出登录」本质是语义化提问，会污染「稀疏通道强项」的结论。现只认 `ERR-\d+` |
| **答案要点限 60 字** | 第一版模型把整个片段当答案要点，导致 ground truth 失去区分度 |
| **JSON 抽取要容错** | 模型常输出 ```json 围栏或前后废话，用「首个 `[` 到末个 `]`」截取 |
| **生成用 9b 而非 4b** | 出题质量直接影响评估集可信度，这里不省时间；且出题是一次性成本 |
| **评估集可重建** | 知识库变更后重跑生成器即可，不必人工重标 |
| **每片段条数不均** | 分布 `{1:1, 2:15, 3:22, 5:2, 6:5, 7:1}` —— 片段信息量不同导致，可接受；若要严格均衡需加裁剪步骤 |

## 7.1 必须知道的局限：合成样本比真实提问「容易」

**Hit Rate 99.39% 看着漂亮，但不能直接当成线上水平。**

原因是合成问题的**用词天然接近源片段**（即使提示里要求别照抄），
而真实用户的提问会更口语、更模糊、还会带错别字和无关上下文。

正确用法：

- ✅ **用于回归比较**：同一套合成集上比较 A/B 配置（换模型、调 top_k、加重排），结论可信；
- ❌ **不要当成绝对水平**：99% 不代表线上 99%。

要得到绝对水平，需要攒一批**真实工单**转成的评估样本。

## 8. 待办 / 注意

- [ ] **缺少相关性门槛**：负样本 100% 会返回 8 条结果，拒答完全依赖生成层。
      需要一批「相关性标注」来校准稠密/稀疏分数阈值，这是当前最实质的缺口。
- [ ] **合成样本未经人工抽检**：14.6% 的答案重复率说明仍有换皮问题，建议人工抽看 20 条确认可用性。
- [ ] **合成样本系统性偏容易**（见 §7.1）：只能用于 A/B 回归比较，不能当绝对水平。
      需攒真实工单样本才能得到线上真实指标。
- [ ] **版本号编造未拦截**：为避免误杀「v5.1」这类合理简写，闸门只管错误码；
      编造版本号（如「v9.9.9 有什么变化」）仍可能混入。
- [ ] **负样本只做了关键词隔离**：未验证「系统确实答不了」，存在少量边界样本
      （如「试用期转正材料」可能与账号权限擦边）。
- [ ] **每片段条数不均**（1~7 条），且有 **1 个片段未被覆盖**；严格均衡需加按片段裁剪/补齐步骤。
- [ ] **评估集的 reference_answer 是片段原话**，用于 RAGAS 的 `reference` 时偏「抽取式」，
      语义相似度评分可能被低估。
- [ ] **`--recreate` 入库会清空集合**：本次扩容依赖它，重复执行同一份文档需先确认 upsert 是否幂等（见 04 篇待办）。
- [ ] **生成评估（含 LLM 回答）尚未在 200 条上全量跑**：单条 ~12s，164 条正样本约 33 分钟，需分批。
- [ ] **切分 overlap=0 与设计文档不一致（已确认是刻意选择，但缺决策记录）**：
      入库日志显示 `overlap=0`，而 `开发流程/04` 写的是「重叠 50 token」。
      核对后确认这是**刻意的**：`ingestion/chunk.py` 的 docstring 说明结构化切分已保证语义边界，
      重叠会引入重复内容、强化模型的错误确信。
      建议补一条 ADR 把这个偏差记下来，否则下次有人对照设计文档会以为是 bug。
