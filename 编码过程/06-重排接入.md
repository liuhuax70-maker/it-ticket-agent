## 4. 功能逻辑（按跳转解释）

### 4.1 为什么是「生成式打分」（方案探索）

**触发点**：动手前先确认 Ollama 上怎么调这个模型。

```
探测结论：
 ① 直接调用 → 输出为空（<think> 占满输出）
 ② 传 "think": false → 输出正常
 ③ 三种问法对比：
      A. yes/no 模板      → "是的，当遇到 ERR-4..."（散文，难解析）
      B. 0~100 整数评分    → "100" / "0"        ← ✅ 采纳
      C. chat + yes/no    → "yes" / "no\n\n<Query>..."（带尾巴）
```

- **采纳方案 B**：输出是纯整数，解析稳定、区分度明显（1.1s / 条）。
- **必须 `think: false`**：这是本节点最大的坑，不加就拿到空字符串。

**技术栈：** Ollama `/api/generate` · `options.num_predict=8` · `temperature=0`

### 4.2 并发打分与限流

**触发点**：`rerank(query, chunks, top_k)`。

```
输入：融合后的候选列表（可能 50 条）

① 切分候选：head = chunks[:rerank_top_n]   （参与重排，默认 20）
              tail = chunks[rerank_top_n:]  （不参与，按原顺序附加到末尾）

② 并发打分（ThreadPoolExecutor，默认 4 并发）
     pool.submit(_score_one, query, chunk, timeout)   ← 每条一次 LLM 调用
        └─ 成功 → 分数 0~100
        └─ 失败 → None + 打日志（单条失败不致命）

③ 失败率守卫：失败条数 > 半数 ──► 抛 RuntimeError
                                    └─► hybrid_search 捕获并跳过重排（三层降级）
```

- **为什么要限流**：重排是**逐条** LLM 调用，50 条 × 1s ≈ 50s，不可接受。限制候选数 + 4 并发把最坏情况压到约 5s（实测 15 条约 7s）。

**技术栈：** `concurrent.futures.ThreadPoolExecutor` · httpx（单条超时 60s）

### 4.3 排序与归一化

**触发点**：分数全部收集完毕后。

```
排序键 = (分数为 None, -分数)
   ├─ 有分数的：按分数**降序**
   └─ 无分数的：排在最后，且保持原有相对顺序（sorted 稳定）
        └─► 单条解析失败不会让该片段消失，只是沉底

写回 Chunk：
   rerank_score = 分数 / 100        # 归一化到 0~1
   rank         = 1, 2, 3, ...      # 重新编号
tail 追加时 rank 继续递增
最终截断到 top_k
```

**技术栈：** Python `sorted`（稳定性语义）· Pydantic `model_copy(update=...)`

### 4.4 三层降级

**触发点**：任一层出错时。

```
第 1 层（单条失败）  → 该条沉底，其余照常
第 2 层（过半失败）  → 抛 RuntimeError → hybrid 跳过重排，沿用融合结果
第 3 层（整体关闭）  → RERANK_ENABLED=false，完全不进重排分支
```

**技术栈：** Python 异常传播 + `hybrid_search` 的 try/except（上一节点已实现）

## 5. 关键实现说明

| 项 | 说明 |
| --- | --- |
| **`think: false` 是硬性要求** | 不加则响应为空字符串，所有候选都会解析失败 → 触发过半失败 → 重排被跳过（表现为「重排静默失效」，很难排查） |
| **解析正则防误判** | `(?<![\w.])(\d{1,3})(?![\d.])`：拒绝「字母/点/数字」相邻的数字，避免把 `v1.2.3` 解析成 1、`2024年` 解析成 202 |
| **尾部标点容忍** | 解析前 `rstrip` 掉 `。.！!？?；;，,` 等，兼容模型输出 `"85."` |
| **越界截断** | 分数 `max(0, min(100, x))`，模型偶尔输出 `150` 也不会越界 |
| **候选限流（`rerank_top_n=20`）** | 重排是 O(n) 次 LLM 调用，必须设上限，否则融合的 50 条会拖垮延迟 |
| **归一化存储** | `Chunk.rerank_score` 存 0~1，与 `dense_score`（余弦）量纲一致，便于观测与展示 |
| **未参与重排的 tail 不丢** | 超过候选上限的片段仍按原顺序附加，避免 `top_k > rerank_top_n` 时结果变少 |

## 7. 验证方式

```bash
pytest -q            # 62 passed（RRF 4 + 切分 16 + 集合 11 + 混合 11 + 重排 20）
```

**单元测试覆盖：**

| 用例 | 期望 |
| --- | --- |
| `_parse_score` 12 组参数化 | 正常/越界/负数/尾部标点/年份/版本号 |
| 文档截断 | 超长文档被截到 1500 字符 |
| 按分数降序 | 顺序与 `rank` 正确，`rerank_score` 归一化 |
| Top-K 截断 / 空输入 | 边界正确 |
| 候选上限 + tail 保留 | 只对前 N 条打分，其余不丢 |
| 单条失败 | 沉底且 `rerank_score=None` |
| 过半失败 | 抛 `RuntimeError` |
| 候选上限取配置 | 与 `settings.rerank_top_n` 一致 |

**真实环境对比（15 个片段，Top-8）：**

```
■ 为什么我的账号登不上，一直提示错误
  [重排关闭]  faq#4 → manual#2 → faq#3 → manual#4 → T-1004 → T-1003 → T-1001 → manual#1
  [重排开启]  faq#4 → manual#2 → faq#3 → T-1002★ → manual#4 → T-1004 → T-1003 → T-1001
              ★ T-1002 原本不在 Top-8，被重排提升到第 4（rerank=1.00）；
                同时 4 条无关片段被打到 0.00 沉底

■ 令牌过期了要重新登录吗
  [重排关闭]  T-1001 → manual#2 → T-1002 → faq#1 → manual#1 → faq#2 → T-1004 → faq#4
  [重排开启]  T-1001 → manual#2 → T-1002 → faq#1 → manual#1 → faq#2 → manual#3★ → T-1004↓
              ★ manual#3 原本不在 Top-8，被提升到第 7；
                ↓ T-1004 从第 7 掉到末位（rerank=0.00）
```

**延迟对比：**

| 场景 | 耗时 |
| --- | --- |
| 重排关闭 | 0.79 ~ 0.95s |
| 重排开启（15 条候选，4 并发） | 6.80 ~ 7.42s |

> 结论：重排**确实能提升精确率**（把 RRF 漏掉的相关片段提上来、把无关片段压下去），但**延迟增加约 8 倍**，因此保持 `RERANK_ENABLED=false` 作为默认，按需开启。

## 8. 待办 / 注意

- [ ] **延迟代价显著**：15 条候选就要 ~7s。若开启重排，建议同时把 `rerank_top_n` 降到 10 以内，或改用带 batch 的专用 reranker 服务。
- [ ] **分数区分度偏「二值」**：实测大量 1.00 / 0.00，中间值少。这与 4B 量化模型 + 简短 Prompt 有关；后续可尝试让模型输出更细粒度分数或改用 logits。
- [ ] **`think: false` 依赖 Ollama 版本**：老版本可能不认该字段；换环境需回归验证（本次在宿主机 Ollama 上验证通过）。
- [ ] **未实现重排整体超时**：目前只有单条超时（60s），整体耗时由「候选数 ÷ 并发 × 单条耗时」决定，没有全局预算控制。
- [ ] **未做重排前后效果量化**：目前只做了顺序对比，缺少「Top-K 命中率提升多少」的量化指标，需配合评估集。
- [ ] **每节点一处「魔法数字」**：`num_predict=8`、`MAX_DOCUMENT_CHARS=1500` 尚未配置化。
