# 编码过程 · 说明与模板

> 目录用途：记录项目编码过程中**每一次加入的框架与功能**，作为「代码是怎么长出来的」的过程档案。
> 与 `开发流程/` 的区别：`开发流程/` 是**事前设计**（要做什么、怎么设计），本次目录是**事中记录**（实际加入了什么、怎么串起来的）。
> 建立日期：2026-09-30

---

## 1. 记录标准（每篇文档必须满足）

### 标准一：从底层到总体

- 先交代**这一层/这个模块在整体布局中的位置**，再往上讲它如何被上层使用。
- 每篇文档需给出**当前项目整体布局**（目录树），让人一眼掌握全局，而不是只见树木。
- 阅读顺序建议由底层向上：基础设施 → 数据/检索 → 生成 → 编排 → 接口 → 部署 → 观测。

### 标准二：按「逻辑跳转」解释功能

- 不使用平铺直叙的说明，而是还原**调用链与跳转过程**：
  `触发点 → 经过哪些模块 → 在哪里跳转/分流 → 产出什么 → 交给谁`。
- 遇到分支（如条件路由、异常降级），要用「什么条件下跳到哪里」的方式写清楚。
- 尽量配一张流程/调用示意，让跳转路径可视化。

### 标准三：标注技术栈

- **每一个新加入的功能，其描述下方必须标注用到的技术栈**，格式统一为：

  ```
  **技术栈：** 语言/框架 · 库 · 外部服务
  ```

- 若该功能涉及多个环节，可分环节标注。

## 2. 命名与编号约定

| 约定 | 说明 |
| --- | --- |
| 目录 | `编码过程/` |
| 文件名 | `NN-<模块或功能名>.md`（与 `开发流程/` 一致使用两位数字前缀） |
| 编号含义 | **按加入顺序**递增，一次「加入一个框架/功能」通常对应一篇 |
| 编号示例 | `01-项目骨架与依赖.md`、`02-配置系统.md`、`03-Milvus-Collection-与入库.md` |
| 模板 | 本文件即模板，新文档复制 §3 结构填写 |

> 若一次加入了多个强相关功能（如同一框架的多个能力），可合并为一篇，但每个功能仍须单独满足「标准三：标注技术栈」。
